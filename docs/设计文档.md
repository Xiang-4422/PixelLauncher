# PixelLauncher 设计文档

## 设计目标

项目采用“产品宿主 + 统一 SDK”结构：`app` 保持业务敏捷，`pixel-engine` 提供稳定、可发布的像素 UI 能力。模块数量不是分层工具；源码职责通过 package、接口、可见性和测试表达。

## 依赖规则

```text
app
 └── pixel-engine
      ├── pixelcore
      ├── pixelui runtime / widgets
      ├── navigation
      ├── Android Host
      ├── testing
      └── debug
```

- `pixel-engine` 不得反向依赖 `app`。
- `app` 只使用 SDK 公开 API。
- 引擎内部包可以分层，但不形成额外 Gradle project 或 Maven coordinate。
- Compose 不是当前 SDK 边界；若未来接入，应以不污染核心 ABI 的独立仓库或经过评审的适配方案实现。

## 渲染模型

引擎采用 retained-mode 三层结构：

1. Widget 描述不可变配置。
2. Element 管理挂载、更新、Inherited 依赖和状态生命周期。
3. RenderObject 执行约束布局、绘制、命中测试与语义投影。

Android Host 负责把像素缓冲提交到 View，并桥接帧时钟、触摸、键盘、IME、窗口 Insets、Lifecycle 和 Accessibility。

## 组件与主题

标准组件只依赖通用 token 和状态集合。产品主题可从 `app` 注入，但组件不得硬编码 Launcher 文案或业务状态。新增组件至少需要：

- 稳定的公开参数和默认值。
- disabled、focused、pressed 等必要状态。
- 布局、交互和像素输出测试。
- API 手册中的最小使用示例。

## 动画

动画由可注入的帧调度器驱动。生产环境使用 `Choreographer`，测试使用手动时钟。动画状态必须可取消、可释放，且不得在 detach 后继续持有 Host 或回调。

## 路由与恢复

路由 API 使用 typed entry/destination，返回栈状态必须可序列化恢复。返回键先由 overlay 和子导航消费，再交给宿主。深链解析与路由 mutation 需要正向行为测试和类型负例消费者。

## 扩展性

高级扩展通过公开 RenderObject SPI、资源加载器、字体/字形提供器、主题 token 和 Host 配置实现。扩展点需满足：

- 不要求访问 `internal` 类型。
- Kotlin 与 Java 调用边界明确。
- R8 后仍可链接。
- 生命周期和资源所有权可说明、可测试。

## 兼容与发布

统一 Maven 坐标不代表放弃边界。以下门禁共同控制演进：

- API/ABI baseline 防止无意破坏。
- `internal` 和稳定 API 分层限制实现泄漏。
- 隔离消费者验证真实 POM/AAR，而非 project dependency。
- 旧消费者二进制测试验证冻结描述符。
- 产物预算防止统一 AAR 无限制膨胀。

## 性能边界

当前工程只保留必要的正确性和产物预算，不把 benchmark 模块纳入主工程。未来性能目标应单独定义设备、场景、采样方法、阈值和噪声处理，再决定是否引入独立性能工程。
