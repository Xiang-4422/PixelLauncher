# Pixel Engine 长期规划

本文只记录尚未完成的长期方向，不重复已经落地的 1.0 能力和历史验收过程。具体开发任务应在开始时
建立新的 Goal，并以当时源码、测试和支持矩阵重新审计。

## 当前基线

主工程当前包含四个 Gradle 模块：

<!-- architecture-contract:modules:start -->
- `:app`
- `:pixel-engine`
- `:showcase`
- `:showcase-desktop`
<!-- architecture-contract:modules:end -->

- `pixel-engine` 仍是统一的 Engine Android Library；两个展示宿主是消费者，不代表 SDK 按职责拆分。
- SDK 只发布一个 `pixel-engine` 坐标。
- retained tree、Android Host、主题、标准组件、动画、路由、恢复、资源、测试和诊断 API 已进入 1.0
  本地候选。
- 性能专项和真实公共发布不属于当前已完成范围。

## P1：真实发布

- 确认 Maven Central namespace 所有权。
- 配置长期或受管 OpenPGP 签名身份。
- 绑定远端 required checks、tag、Release notes 和版本化文档站。
- 执行真实 staging/close/publish，并用全新消费者复验不可变坐标。

这类操作需要维护者明确授权，不能由本地签名演练替代。

## P2：独立性能目标

- 定义代表性设备、Android 版本、刷新率和温控条件。
- 为启动、列表滚动、文本输入、动画、导航和大资源建立可重复场景。
- 区分 JVM 算法、microbenchmark、macrobenchmark、Perfetto 和长时间 soak。
- 建立噪声处理、回归阈值、基线审批和报告保留规则。
- 评估 Baseline Profile、局部刷新、缓存与批处理策略。

未建立可靠测量前，不把猜测性性能优化加入发布阻断门禁。

## P3：高级组件

候选组件按通用性、无障碍、键盘操作和组合价值排序：

1. `Badge`、`Chip`、`Divider`、`Spacer`、`IconLabel`。
2. `AppBar`、`BottomBar`、`NavigationRail`、`Breadcrumb`。
3. `AnimatedVisibility`、`FocusTraversalGroup`、`ShortcutHint`。
4. `Popover`、`Menu`、`Dropdown`、`Tooltip` 的一致锚点与碰撞策略。
5. 面向数据密集界面的 tree、table、virtualized grid 和 resize handle。

每个组件必须具备中性命名、主题 token、必要状态、RTL/文本缩放、键盘与 semantics、确定性测试和 API
手册示例；不为了数量复制 Launcher 专用控件。

## P4：平台与适配

- 评估 Compose 应用侧适配器是否需要独立仓库或不污染核心 ABI 的发布边界。
- 验证大屏、折叠屏、多窗口、硬件键盘和游戏手柄场景。
- 评估非 Android 离屏运行时，但不提前承诺跨平台 UI 后端。
- 扩展字体 shaping 和复杂脚本覆盖，明确内置 glyph 与完整字体引擎的边界。

## P5：开发者体验

- 自动生成可搜索 API reference，减少手工 API 清单漂移。
- 提供最小示例 app 或外部 sample 仓库，不向主工程重新引入 demo 模块。
- 改进错误诊断、Inspector 导出和可复现问题报告。
- 为自定义 RenderObject、资源包和主题扩展提供模板与静态检查。

## 不采用的方向

- 不恢复按 core/runtime/widgets/navigation 等职责拆分的 Gradle 模块。
- 不在 Engine 中引入 Launcher 业务模型或 Material/Cupertino 兼容层。
- 不把任意 Composable 嵌入 Pixel retained tree。
- 不用模糊截图或手工观感替代确定性行为、像素和语义测试。
