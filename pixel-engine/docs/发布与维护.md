# Pixel Engine 发布与维护

本文统一定义版本兼容、构建支持、安全响应、供应链和发布核对规则。

## 1. 版本与兼容

1.0 后遵循 SemVer：MAJOR 包含不兼容变化，MINOR 提供向后兼容能力或弃用，PATCH 只包含向后兼容修复。
稳定 API 的 source、binary、默认行为、持久状态格式和可观察时序都属于兼容审查范围。

兼容承诺覆盖：

- `pixel-engine/api/` 中的 Kotlin、Metalava 和 JVM binary baseline。
- 文档承诺的 Host、组件、路由、资源、测试和高级 SPI 行为。
- 发布 POM/AAR、consumer rules 与支持矩阵。

不覆盖 `internal` 实现、Launcher 业务代码、构建目录报告和未进入 baseline 的测试 helper。

## 2. 实验与弃用

实验 API 必须使用 `@PixelExperimentalApi`，并具备中文 KDoc、行为测试、示例和 Changelog。稳定化前
至少经过一个公开 minor 的消费者验证。

稳定 API 删除前必须：

1. 添加 Kotlin `@Deprecated` 和可用的 `ReplaceWith`。
2. KDoc 说明原因、替代 API 和最早移除版本。
3. 在 `CHANGELOG.md` 记录。
4. 至少保留一个完整 minor；通常在后续第二个 minor 或下一个 major 删除。
5. 删除时同时提供 baseline diff、迁移说明和兼容测试。

只有阻止正在利用的安全问题、崩溃或数据损坏时才允许缩短周期。

## 3. 消费者支持矩阵

| 项目 | 1.0 契约 |
|---|---|
| minSdk | 24 |
| compileSdk 硬下限 | 36 |
| 推荐 compileSdk | 36.1 |
| AAR 最低 AGP | 8.10.0 |
| 最低已验证组合 | Kotlin 2.2.10 / AGP 8.10.1 / Gradle 8.11.1 / JDK 17+ |
| 推荐组合 | AGP 9.1.1 / Gradle 9.3.1 / JDK 21 |
| Producer | AGP 9.0.1 / Gradle 9.1.0 / JDK 21 |

提高 minSdk、compileSdk、Kotlin、AGP、Gradle 或 JDK 下限必须进入 MINOR/MAJOR，并同步 AAR metadata、
Changelog、迁移指南和消费者矩阵。

## 4. 发布产物与供应链

唯一正式坐标是 `com.purride:pixel-engine:<version>`，包含 AAR、POM、Gradle module metadata、sources
和 Javadoc/KDoc。

`pixel-engine/config/release-metadata.properties` 是项目、SCM、developer、issue tracker 和许可证信息
的唯一来源。仓库使用 Apache-2.0，`LICENSE` 与 `NOTICE` 摘要受固定校验。

`pixel-engine/gradle.lockfile` 固定 release compile/runtime 版本；`gradle/verification-metadata.xml`
固定依赖内容摘要。升级依赖时必须单独审阅 version、lockfile 和 verification metadata diff。

供应链门禁生成：

- CycloneDX 1.7 SBOM。
- in-toto/SLSA provenance。
- Maven 主体和补充物的 checksum。
- OpenPGP 签名与隔离 keyring 验证。
- 只读 HTTP Maven 最低/推荐消费者矩阵。

```bash
bash tools/pixel-supply-chain-check.sh
```

候选 groupId `com.purride` 在公共发布前仍需证明 namespace 所有权。演练密钥与本地 staging 只证明
流水线可用，不代表真实发布授权。

## 5. 构建来源契约

发布输入包括当前 Git commit/tree、Engine 版本、release lockfile、dependency verification SHA-256
以及由环境变量注入的签名与 Maven 凭据。正式输出不得使用 dirty worktree、临时签名身份或 SNAPSHOT
文件名。provenance 的 buildType 指向本文，步骤为解析依赖、生成 publication、签名、生成 SBOM/
provenance/checksum、独立验签和外部消费。

## 6. 安全支持与响应

1.0 发布后，默认支持最新 minor 的最新 patch；上一 minor 在新 minor 发布后的 90 天内接受安全
backport，除非 release notes 另有声明。

漏洞通过 GitHub Security 私密 advisory 报告，不在公开 issue 中提交利用步骤、凭据或个人数据。
维护流程：确认与隔离、评估严重度和受影响版本、准备最小修复、运行完整非性能门禁、生成不可变新版本、
协调披露。任何泄露的签名或仓库凭据必须立即吊销，不得继续用于发布。

## 7. 发布清单

- [ ] 版本号与 Changelog 条目一致，正式版本含 ISO 日期。
- [ ] API/ABI diff 已审阅；breaking change 有弃用和迁移说明。
- [ ] JVM、Lint、instrumentation、隔离消费者与 R8 通过。
- [ ] AAR/POM/module/sources/Javadoc 和产物预算通过。
- [ ] LICENSE、NOTICE、SBOM、provenance、checksum、签名和 OSV 通过。
- [ ] 工作区干净，commit、tag、Release notes 和文档版本一致。
- [ ] 正式 namespace、长期签名身份和远程仓库已由维护者明确授权。

```bash
bash tools/pixel-release-check.sh
```

当前已完成本地候选工程；真实 Maven 发布、namespace、长期签名、tag、Release 和发布后复验留给独立
发布任务。性能 benchmark、trace 与 soak 也不属于当前发布门禁。
