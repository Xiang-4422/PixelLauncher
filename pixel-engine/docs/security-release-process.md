# 安全修复与发布流程

安全问题不走公开 issue 的普通排队流程。报告者应优先使用仓库 GitHub Security 的私密 advisory；在
维护者确认可以公开之前，不在 issue、讨论区或提交信息中披露利用细节。

## 分级与响应

| 级别 | 示例 | 首次分诊目标 | 发布通道 |
|---|---|---:|---|
| Critical | 可远程执行、真实密钥泄漏、普遍数据破坏 | 24 小时内 | 最快安全 patch |
| High | 可利用越界、权限/隐私绕过、稳定拒绝服务 | 2 个工作日内 | 优先 patch |
| Medium/Low | 需要强前提或影响有限 | 5 个工作日内 | 正常 patch/minor |

响应目标不是修复完成承诺；首次分诊必须确认影响版本、可利用前提、临时缓解和下一次更新时间。

## 修复分支

- 从仍受支持的最近发布 tag 创建私有修复分支。
- 不在公开 CI 日志、测试名称、fixture 或提交信息中放入可直接复现的敏感 payload。
- 添加最小回归测试、secret scan、依赖验证、OSV、AAR 内容和 consumer 证据。
- 若稳定 API 必须立即改变以阻止崩溃、数据损坏或利用，允许跳过常规弃用周期，但必须记录受影响
  API、原因、替代方案和迁移步骤。
- 同一修复按仍受支持版本逐一 backport；不得用重新上传相同 Maven 版本覆盖已发布文件。

## 发布与披露

1. 运行完整 release、设备、性能和供应链门禁。
2. 用正式密钥签名候选，独立复核 POM/SBOM/provenance/checksum。
3. 发布新的不可变 patch/minor 版本。
4. 从全新消费者验证坐标与缓解措施。
5. 与报告者协调公开 advisory、CVE/OSV（适用时）、受影响版本和修复版本。
6. 轮换任何可能暴露的密钥/令牌，并审计 Git 目标历史和 CI 日志，而不只删除工作树文件。

安全例外、普通 deprecation 和 breaking change 的版本规则见[发布与兼容策略](发布与兼容策略.md)。
