# pixel-engine 彩色系统实现计划

> 本文档面向**接手实现彩色系统的开发者**。彩色系统比动画系统复杂得多——它涉及渲染层最底层存储格式、主题体系重构、所有公开 widget 的 API 扩展、与 Mono 模式的兼容性承诺。所有取舍已经在本文档里收敛。

最后更新：2026-05-20

---

## 0. 你是谁，你要做什么

你接手 pixel-engine 彩色系统的实现。SDK 维护者已经就方向、取舍、依赖关系达成共识，你的任务是把 Phase A → Phase E 五个阶段按下面的步骤落地。

**前置条件**：动画系统（[动画实现计划](动画实现计划.md)）已完成并稳定运行至少一个版本。彩色系统会让 `Tween<T>` 体系新增 `PixelColorTween`，需要动画基类已经为扩展留好位。

**关键纪律**：彩色系统涉及的架构决策回退成本极高（buffer 存储格式、token 抽象方式）。如果实现过程中发现某个取舍不合理，**先停下来，回到 `色彩演进.md` §9 开放问题里讨论，确认变更，更新本文档，再继续**。绝不允许在实现里偷偷改方向。

## 2. 范围

本计划覆盖 [色彩演进](色彩演进.md) §8 的 Phase A → Phase E：

- **Phase A**：渲染层基础设施（PixelColor / 双类型 PixelBuffer / blit / pool）
- **Phase B**：主题与 token 重构（tokens 增加 PixelColor 字段、resolveXxxStyle 加 colorMode 参数）
- **Phase C**：公开 widget API 扩展（Container / Text / PixelTextStyle 等增加 color 参数）
- **Phase D**：Mode 切换 + Host 集成（PixelColorMode 枚举 + PixelHostSetupConfig.colorMode + HostView 渲染管线分流）
- **Phase E**：文档 / 验收（更新所有相关文档、新增 demo scene、跑性能基线、彩色专属 golden）

**不覆盖**（参见 `色彩演进.md` §7）：

- 子树级 mode 切换（一棵树内部分彩色 + 部分单色）—— 明确不做
- HDR / 10-bit / sRGB / Display-P3 色彩管理 —— 明确不做
- 渐变填充（linear / radial gradient）—— 等彩色模式稳定后再单独立项
- 像素位深可配置（4-bit / 8-bit 调色板模式）—— 明确不做
- Mono → Color 自动迁移工具 —— 明确不做
- 动态切换 mode（运行时切换 colorMode）—— 暂不做，Phase D 仅支持构造时确定

## 3. 已定的设计取舍（不要再讨论）

`色彩演进.md` §9 列出了 7 个开放问题。本文档作为实现合同，把这 7 个决策**全部锁定**：

### 3.1 PixelColor / PixelTone 互转走显式 tokens

**决策**：必须显式 `tokens.colorFor(tone): PixelColor`，不提供 `tone.toPixelColor(theme)` 隐式转换。

**理由**：隐式映射会导致同样的 widget 在不同 theme 下视觉漂移，难以追踪源头。

**实施约束**：`PixelTone` 不允许新增 `toPixelColor()` 扩展函数。任何 tone → color 转换必须在调用方显式传入 tokens 或 themeData。

### 3.2 tokens 走并存字段，不走统一抽象

**决策**：`PixelThemeTokens` 同时持有 `tone: PixelTone` 字段（兼容现有）和 `color: PixelColor?` 字段（彩色补充），由 `colorMode` 决定运行时读哪个。

**理由**：选项 A（统一抽象 + Mono 反向量化 PixelColor 回 PixelTone）会让 Mono 模式承担一次"颜色到色阶的量化"开销，且量化算法本身有歧义（如何把 ARGB 映射回 3 档？）。选项 B 字段翻倍是可接受代价。

**实施约束**：每个现有 token 字段（如 `textTone`、`borderTone`、`accentBorderTone`）必须同时新增对应的 `xxxColor: PixelColor?` 字段，命名规则 `<原名替换 Tone 为 Color>`。

### 3.3 Mono 模式下传 color 参数 → debug 抛、release fallback

**决策**：

- Debug 构建：检测到 Mono 模式下用户传非空 `color` 参数，立即抛 `IllegalStateException`，定位到具体 widget。
- Release 构建：silently fallback 到 tone，不 log。

**理由**：让开发期立即暴露错误用法；生产环境保证稳定不崩。

**实施约束**：判断 debug 的方式用 `BuildConfig.DEBUG`（pixel-engine `:assembleDebug` / `:assembleRelease` 各自的 BuildConfig）。所有公开 widget 函数体内做这个检查。

### 3.4 PixelBuffer 拆双类型，不走统一接口

**决策**：

- `PixelBuffer` 保留作为公开**接口或 sealed parent**，包含 `width`、`height`、`clear()`、`blit()` 等通用方法。
- 新增 `MonoPixelBuffer` 实现：内部 `ByteArray`，每像素 1 字节 0/1/2。**完全等价当前实现**。
- 新增 `ColorPixelBuffer` 实现：内部 `IntArray`，每像素 4 字节 ARGB。
- 渲染管线按 `PixelColorMode` 在构造时决定用哪个实现。

**理由**：统一接口必然引入 `mode` 字段 + 每次 setPixel 做 mode 分支，热路径开销不可接受。

**实施约束**：

- 任何 RenderObject 的 paint 代码不应通过 `if (buffer is MonoPixelBuffer)` 分支——而应直接调用 PaintContext 提供的 mode-agnostic API（`setTone` / `setColor`，由 PaintContext 内部分流到对应 buffer 类型）。
- 双类型 buffer 互不通用：Mono buffer 不能转 Color，反之亦然。

### 3.5 不做彩色模式 compatibility palette

**决策**：彩色模式下不提供"5 预设主题的彩色等价版"。

**理由**：彩色用户期望自由配色；强行套预设别扭。但 demo 可以提供"彩色版 GREEN_PHOSPHOR"等示例 tokens 供参考——这是 demo 的事，不是 SDK 的事。

**实施约束**：`PixelPalette` 在 Color 模式下完全不被使用。`PixelTheme` 5 个预设枚举值在 Color 模式下仅作为 tokens 选择器。

### 3.6 不支持动态切换 mode

**决策**：Mode 在 `PixelHostSetupConfig` 一次性确定，运行时不可改。

**理由**：动态切换会让 buffer pool / RenderObject 缓存 / 字体栅格全部失效，引入难以排查的边界 bug。如果用户要切换，可销毁 PixelHostView 重新构造。

**实施约束**：`PixelHostSetupConfig.colorMode` 一旦传入，PixelHostView 生命周期内不暴露 setter；`PixelHostBridge` 也不允许后置 set。

### 3.7 彩色模式保留 5 预设主题作为示例 tokens

**决策**：`PixelTheme` 枚举（GREEN_PHOSPHOR / AMBER_CRT / ICE_LCD / MONO_LCD / NIGHT_MONO）在 Color 模式下仍然有效，每个预设的 `PixelThemeTokens` 中 `color: PixelColor?` 字段在 SDK 端给出一个**默认彩色映射**（例如 GREEN_PHOSPHOR 的 textColor 默认是绿色调）。

**理由**：即使是自由配色场景，提供"可参考的色彩搭配"对入门用户也有价值。

**实施约束**：5 个预设的彩色版默认值由 SDK 维护者审美决定，不在本计划讨论具体颜色值——Phase B 落地时在 PR 里 review。

## 4. Phase A — 渲染层基础设施

**目标**：在不动任何公开 widget API 的前提下，把 `PixelBuffer` 拆为双类型，并新增 `PixelColor`。

### 4.1 文件清单

新建：

```
├── MonoPixelBuffer.kt      （新增，吸收原 PixelBuffer 的 ByteArray 实现）
└── ColorPixelBuffer.kt     （新增）
```

修改：

```
pixel-engine/src/main/kotlin/com/purride/pixelcore/graphics/
├── PixelBuffer.kt          （重构为 sealed interface 或 abstract class）
└── PixelBufferPool.kt      （按 (w, h, mode) 索引）
```

### 4.2 PixelColor

```kotlin
@JvmInline
public value class PixelColor(public val argb: Int) {
    public val alpha: Int get() = (argb ushr 24) and 0xFF
    public val red: Int get() = (argb ushr 16) and 0xFF
    public val green: Int get() = (argb ushr 8) and 0xFF
    public val blue: Int get() = argb and 0xFF

    public companion object {
        public fun fromArgb(a: Int, r: Int, g: Int, b: Int): PixelColor
        public fun fromRgb(r: Int, g: Int, b: Int): PixelColor    // alpha = 0xFF
        public val Transparent: PixelColor = PixelColor(0)
    }
}
```

**实施约束**：

- `value class` 优先于 `data class`——零 boxing 开销在热路径上。
- 不提供预定义颜色常量（如 `PixelColor.Red`）。用户要红色就写 `PixelColor.fromRgb(255, 0, 0)`。理由：SDK 不替用户决定调色板。
- 不提供 `lerp(a, b, t)` 函数——颜色插值在 `PixelColorTween` 里做，不污染 PixelColor 自身。

**测试必须覆盖**：

- argb 通道分解正确（边界值 0 / 255）。
- `fromArgb(255, 255, 0, 0).argb == 0xFFFF0000.toInt()`。
- `Transparent.alpha == 0`。

### 4.3 PixelBuffer（重构）

```kotlin
public sealed interface PixelBuffer {
    public val width: Int
    public val height: Int
    public val mode: PixelColorMode      // Phase D 才引入，Phase A 临时用 sealed 子类区分
    public fun clear()
    public fun blit(source: PixelBuffer, destX: Int, destY: Int)
}
```

**实施约束**：

- 现有 `PixelBuffer(width, height)` 构造函数移到 `MonoPixelBuffer`——这是破坏性 API 变更，但 internal 使用方都在 SDK 内部，可以一并改。
- `setPixel(x, y, toneValue: Int)` 这种原始 API 不进 `PixelBuffer` 接口——只在 `MonoPixelBuffer` 暴露 `setPixel(x, y, PixelTone)`，在 `ColorPixelBuffer` 暴露 `setPixel(x, y, PixelColor)`。这样误调用在编译期就报错。

### 4.4 MonoPixelBuffer

```kotlin
public class MonoPixelBuffer(
    override val width: Int,
    override val height: Int,
) : PixelBuffer {
    public val pixels: ByteArray   // 暴露给 Android 渲染层（PixelFrameView）使用
    public fun setPixel(x: Int, y: Int, tone: PixelTone)
    public fun getPixel(x: Int, y: Int): PixelTone
    override fun clear()           // 全部填 OFF (0)
    override fun blit(source: PixelBuffer, destX: Int, destY: Int)
}
```

**实施约束**：

- `MonoPixelBuffer` 的实现必须**逐字节对齐**原 `PixelBuffer` 的字节布局——Phase A 验收的关键就是 Mono 模式下所有 golden 测试无任何字节差异。
- blit 处理同类型时走原 `arraycopy`；处理 `ColorPixelBuffer` 时抛 `UnsupportedOperationException("Cannot blit Color buffer into Mono buffer")`。

### 4.5 ColorPixelBuffer

```kotlin
public class ColorPixelBuffer(
    override val width: Int,
    override val height: Int,
) : PixelBuffer {
    public val pixels: IntArray
    public fun setPixel(x: Int, y: Int, color: PixelColor)
    public fun getPixel(x: Int, y: Int): PixelColor
    override fun clear()           // 全部填 Transparent (argb = 0)
    override fun blit(source: PixelBuffer, destX: Int, destY: Int)
}
```

**实施约束**：

- blit 同类型走 `System.arraycopy(IntArray)`。
- alpha blend：Phase A 不实现真 alpha blend，blit 走简单覆盖（dest = source）。真 alpha 留给后续增量任务。
- blit 处理 `MonoPixelBuffer` 时抛 `UnsupportedOperationException("Cannot blit Mono buffer into Color buffer")`。

### 4.6 PixelBufferPool（重构）

```kotlin
public class PixelBufferPool {
    public fun acquireMono(width: Int, height: Int): MonoPixelBuffer
    public fun acquireColor(width: Int, height: Int): ColorPixelBuffer
    public fun release(buffer: PixelBuffer)
}
```

**实施约束**：

- 内部按 `(w, h, mode)` 三元组索引；Mono 和 Color 不共享池条目。
- `release` 根据 buffer 的具体类型路由到对应池。
- 现有调用方（`PixelRenderSessionFactory` 等）调用 `acquireMono` 来保持兼容。

### 4.7 Phase A 测试必须覆盖

- `MonoPixelBuffer` setPixel / getPixel / clear / blit 与原 `PixelBuffer` 行为完全一致——直接复制现有 `PixelBufferTest.kt` 改名跑。
- `ColorPixelBuffer` setPixel / getPixel / clear / blit 基础正确。
- 跨类型 blit 抛 UnsupportedOperationException。
- `PixelBufferPool.acquireMono` / `acquireColor` 池化命中 / 未命中行为正确。
- 现有所有 golden 测试（`pixel-engine/src/test/kotlin/com/purride/pixelui/regression/`）**零字节变化**——这是 Phase A 验收的硬指标。

## 5. Phase B — 主题与 token 重构

**目标**：让 `PixelThemeTokens` 同时携带 PixelTone 和 PixelColor 字段；`resolveXxxStyle` 按 colorMode 选择性返回。

### 5.1 PixelColorMode（提前在此引入）

```kotlin
public enum class PixelColorMode { Mono, Color }
```

文件位置：`pixel-engine/src/main/kotlin/com/purride/pixelcore/graphics/PixelColorMode.kt`。

Phase D 才真正作用在 HostSetupConfig 上，Phase B 先用于 tokens 解析。

### 5.2 PixelThemeTokens 重构

当前每个 token 字段类型是 `PixelTone`。重构后并存字段：

```kotlin
public data class PixelThemeTokens(
    public val textTone: PixelTone,
    public val textColor: PixelColor? = null,           // 新增
    public val accentTextTone: PixelTone,
    public val accentTextColor: PixelColor? = null,     // 新增
    public val borderTone: PixelTone,
    public val borderColor: PixelColor? = null,         // 新增
    // ... 所有现有 *Tone 字段都加对应 *Color: PixelColor? = null
)
```

**实施约束**：

- 命名规则：原 `xxxTone` 新增对应 `xxxColor: PixelColor?`，**默认 null**。
- null 含义：彩色模式下没有提供等价颜色，由 `resolveXxx` 决定行为（见 §5.3）。
- 5 个预设主题（GREEN_PHOSPHOR / AMBER_CRT / ICE_LCD / MONO_LCD / NIGHT_MONO）必须各自填上 PixelColor 默认值（颜色由 PR review 决定）。

### 5.3 resolveXxxStyle 加 colorMode

每个 resolve 方法签名扩展：

```kotlin
public fun PixelThemeData.resolveTextStyle(
    override: PixelTextStyle? = null,
    colorMode: PixelColorMode = PixelColorMode.Mono,
): PixelTextStyle
```

**行为规则**：

- `colorMode = Mono`：完全等价当前行为，只看 tone 字段。
- `colorMode = Color`：
  - 如果 override 提供了 color → 用 override.color。
  - 否则如果 tokens.textColor != null → 用 tokens.textColor。
  - 否则 → 抛 `IllegalStateException("Color mode requires textColor in tokens or override")`——这是 SDK 配置错误，不能 silently fallback。

**实施约束**：

- 默认参数 `colorMode = Mono` 保证调用方零迁移。
- 任何在 Color 模式下用到的 token 必须事先填好 color 字段，否则爆。

### 5.4 PixelTextStyle 扩展

```kotlin
public data class PixelTextStyle(
    public val tone: PixelTone = PixelTone.ON,
    public val color: PixelColor? = null,        // 新增
    public val letterSpacing: Int = 0,
    public val lineHeight: Int? = null,
    public val fontScale: Int = 1,

```

**实施约束**：

- `color` 默认 null。Mono 模式忽略；Color 模式优先级高于 tone。
- 不删除 `tone` 字段——保持向后兼容。

## 6. Phase C — 公开 widget API 扩展

**目标**：所有面向用户的 widget 函数追加 `color: PixelColor? = null` 参数；不破坏现有调用。

### 6.1 受影响的 widget 清单

新增 `color` 参数的公开 widget（位于 `pixel-engine/src/main/kotlin/com/purride/pixelui/widgets/`）：

- `Container` / `OutlinedContainer`
- `Text` / `RichText`
- `PixelButton` / `OutlinedButton`
- `PixelTextField`
- 所有 `Animated*` widget 的 `borderColor` 等 color-related 属性（如已实现）

### 6.2 API 扩展模式

每个 widget 函数追加参数：

```kotlin
public fun Container(
    child: Widget? = null,
    width: Int? = null,
    height: Int? = null,
    padding: EdgeInsets? = null,
    background: PixelTone? = null,            // 现有
    backgroundColor: PixelColor? = null,      // 新增
    borderTone: PixelTone? = null,            // 现有
    borderColor: PixelColor? = null,          // 新增
    // ...
): Widget
```

**实施约束**：

- 命名规则：原 `xxx: PixelTone` 对应新增 `xxxColor: PixelColor?`。
- 函数体内：根据当前 `PixelColorMode`（从 InheritedWidget 或 PaintContext 拿到）决定用哪个。
- Mono 模式下用户传非空 color 参数：调用 `checkColorParamInMono()` 工具函数（见 §6.3）。

### 6.3 Mono 模式下传 color 的检查工具

新建 `pixel-engine/src/main/kotlin/com/purride/pixelui/internal/util/ColorParamGuard.kt`：

```kotlin
internal fun checkColorParamInMono(
    widgetName: String,
    paramName: String,
    color: PixelColor?,
    colorMode: PixelColorMode,
) {
    if (color != null && colorMode == PixelColorMode.Mono) {
        if (BuildConfig.DEBUG) {
            throw IllegalStateException(
                "$widgetName.$paramName is set but PixelColorMode is Mono. " +
                    "Either remove the color parameter or set colorMode = Color in PixelHostSetupConfig."
            )
        }
        // release：silently ignore
    }
}
```

每个 widget 函数体内对每个 color 参数调用此 guard。

### 6.4 PaintContext 扩展

```kotlin
public interface PixelPaintContext {
    public val buffer: PixelBuffer
    public val colorMode: PixelColorMode

    public fun setTone(x: Int, y: Int, tone: PixelTone)
    public fun setColor(x: Int, y: Int, color: PixelColor)
}
```

**实施约束**：

- `setTone` 在 Color 模式下 → 通过当前 theme tokens 把 tone 映射到 color 再落 buffer。
- `setColor` 在 Mono 模式下 → 抛 `IllegalStateException("setColor called in Mono mode")`（debug） 或 fallback 到 nearest tone（release——但 nearest 算法暂定为：alpha < 128 → OFF，否则 ON。具体策略 PR review）。

### 6.5 PixelColorTween（新增）

按 [动画方向](动画方向.md) §3.6 已留位，在彩色系统这里实装：

文件：`pixel-engine/src/main/kotlin/com/purride/pixelui/animation/PixelColorTween.kt`

```kotlin
public class PixelColorTween(
    begin: PixelColor,
    end: PixelColor,
) : Tween<PixelColor>(begin, end) {
    override fun lerp(t: Float): PixelColor {
        // 各通道线性插值
        val a = lerpChannel(begin.alpha, end.alpha, t)
        val r = lerpChannel(begin.red, end.red, t)
        val g = lerpChannel(begin.green, end.green, t)
        val b = lerpChannel(begin.blue, end.blue, t)
        return PixelColor.fromArgb(a, r, g, b)
    }
}
```

**实施约束**：

- 通道插值用整数 round，不留小数。
- 单测必须覆盖：begin → end，中点是各通道中点；t=0/0.5/1 边界正确。

### 6.6 Phase C 测试必须覆盖

## 7. Phase D — Mode 切换 + Host 集成

**目标**：把 `PixelColorMode` 一路从 `PixelHostSetupConfig` 传到渲染管线最深处，让模式真正生效。

### 7.1 PixelHostSetupConfig

```kotlin
public data class PixelHostSetupConfig(

    public val theme: PixelThemeData = PixelThemeData.greenPhosphor(),
```

### 7.2 PixelHostView 集成

- 构造 `PixelBufferPool.acquireMono/acquireColor` 时按 mode 路由。
- `PixelFrameView`（Android Canvas 绘制层）按 mode 选 `MonoPixelBuffer.pixels` 走调色板 LUT，或 `ColorPixelBuffer.pixels` 直接 setPixels 到 Canvas。

### 7.3 PixelColorModeProvider InheritedWidget

新增 `pixel-engine/src/main/kotlin/com/purride/pixelui/internal/PixelColorModeProvider.kt`：

```kotlin
internal class PixelColorModeProvider(
    public val colorMode: PixelColorMode,
    child: Widget,
) : InheritedWidget(child) { ... }

public fun BuildContext.colorMode(): PixelColorMode
```

由 `PixelHostView` 在 widget 树根注入。widget 函数体内通过 `context.colorMode()` 读取。

### 7.4 PixelFrameView 适配

`PixelFrameView` 当前只处理 `MonoPixelBuffer` 走 palette LUT。需要增加 Color buffer 路径：

```kotlin
internal class PixelFrameView : View {
    private var bitmap: Bitmap

    fun present(buffer: PixelBuffer) = when (buffer) {
        is MonoPixelBuffer -> presentMono(buffer)
        is ColorPixelBuffer -> presentColor(buffer)
    }

    private fun presentMono(buffer: MonoPixelBuffer) { ... }   // 现有逻辑
    private fun presentColor(buffer: ColorPixelBuffer) {
        // bitmap.setPixels(buffer.pixels, ...)
    }
}
```

**实施约束**：

- Mono 路径不允许有任何性能回退。
- Color 路径用 `Bitmap.setPixels(IntArray)`，再 `Canvas.drawBitmap` 缩放到屏幕。
- bitmap 实例按 mode 复用，不在每帧重新分配。

## 10. 已知坑点 / 容易做错的地方

### 10.1 Phase A 必须严格保持 Mono 等价

最容易出问题的是 `MonoPixelBuffer` 重构后字节布局或 blit 行为微小变化，导致下游 golden 集体红。Phase A 完成后第一件事：跑全套 golden，确认零字节差异。

### 10.2 双类型 buffer 不允许互转

不要写"工具方法"把 ColorPixelBuffer 转成 MonoPixelBuffer（或反之）。量化算法没有唯一正确解；引入后会有人滥用，破坏模式承诺。

### 10.3 PaintContext.setColor 在 Mono 模式下不要 silently fallback

Phase C.4 已规定 setColor 在 Mono 模式下 debug 抛、release fallback。但 release 的 nearest 算法本身有歧义。建议：release fallback 时**强制走 OFF**（最低风险），并让开发者知道这是 SDK 配置错误。

### 10.4 InheritedWidget 注入不能漏

`PixelColorModeProvider` 必须由 `PixelHostView` 在最根上注入。如果忘了，所有 `context.colorMode()` 默认返回 Mono，Color 模式下表现为"颜色完全失效"，但不会报错——非常难调。

实施时：`PixelHostView` 构造 widget 树时强制 wrap 一层 `PixelColorModeProvider`。

### 10.5 PixelBufferPool 不要让 Mono 和 Color 共享条目

如果池误把 `(64, 64, Mono)` 的 buffer 返回给 `(64, 64, Color)` 请求，下游会把 ARGB 当成 byte 数组读取——很难定位的随机崩。索引键必须包含 mode，acquire 方法分两个不让外部传错。

### 10.6 5 个预设主题的彩色映射不要拍脑袋决定

GREEN_PHOSPHOR 默认绿色是多绿？accent 是亮绿还是带蓝？这种审美决策不能在实现 PR 里 review 通过——容易后期被翻账。建议 Phase B.2 单独提一个"5 预设彩色映射"的设计 issue，让维护者审核后再合。

### 10.7 性能基线必须按 mode 分开记录

不要把 Color 模式的 perf 数字塞进现有 `perf-baseline.json`——会让 Mono 用户产生"加了彩色后我变慢了"的错觉。两个文件分开（`perf-baseline.json` 和 `perf-baseline-color.json`），threshold 也独立。

### 10.8 Animated 系列 widget 在 Phase C 才能加 color 参数

如果动画系统已经做完，所有 `AnimatedXxx` widget 都不知道彩色——这是预期的。Phase C 是它们加 color 参数的窗口。**不要**在动画实现期就把 color 参数加进去，否则用户拿到一个不工作的 API。

### 10.9 alpha blend 是后续增量

Phase A 的 `ColorPixelBuffer.blit` 不做真 alpha blend，只做覆盖。真 alpha blend 在彩色稳定一个版本后单独立项做——它涉及 ARGB blend 数学、性能、是否需要预乘 alpha 等独立决策。

### 10.10 PixelPalette 不要在 Color 模式下被使用

Phase D 完成后，`PixelPalette` 只在 Mono 路径下生效。确认 `PixelFrameView.presentColor()` 不引用 palette；如果引用了，说明实施时偷懒走了 Mono 量化路径——回到 §3.5 的决策。

- 子树级 mode 切换 —— 明确不做
- Mono → Color 自动迁移工具 —— 明确不做
- 4-bit / 8-bit 多调色板模式 —— 明确不做
