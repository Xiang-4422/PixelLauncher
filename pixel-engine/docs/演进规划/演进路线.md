# pixel-engine 演进路线

> SDK 的演进方向、当前迭代任务、优先级、历史决策。给接手维护 `pixel-engine` 的下一位开发者，也给规划下一阶段时的自己。

> 本文档是当前事实版路线图，不是历史计划的逐字继承。任何任务都需要先按代码事实复核；只有仍然合理、仍然能提升 SDK 可信度或能力的任务才执行。

## 1. 当前结论

`pixel-engine` 已经过了“能不能跑”的阶段，当前重点是产品化：API 可信、文档准确、性能有门禁、demo 能当 release gate。

当前已具备：

- 单模块 `:pixel-engine`，内部保留 `pixelcore` / `pixelui` / `pixelengine` 包边界。
- Flutter 风格 `Widget -> Element -> RenderObject` 三层模型。
- `PixelHostView` 继承 `android.view.View`，不是 `SurfaceView`。
- `explicitApi = Strict` 已启用。
- `pixel-demo` 已覆盖大量公开 widget 和高级扩展场景。
- `ListViewBuilder(itemExtent != null)` 已有固定高度 lazy 路径；`ListViewBuilder(estimatedItemExtent != null)` 已有显式 opt-in 的变高 lazy 路径，并通过 retained `PixelItemExtentIndex` 支持远端窗口定位；`itemExtent == null && estimatedItemExtent == null` 仍是 eager 兼容路径。
- `ListViewSeparatedBuilder` 已支持 item/separator 各自固定或估算高度的 lazy 分隔列表，并通过 retained `PixelSeparatedExtentIndex` 支持远端 virtual row 定位。
- 文本渲染已引入 internal paragraph layout，`Text` / `RichText` 共用测量、断行和 ellipsis 语义；`PixelTextStyle` 已支持 `letterSpacing`、`lineHeight`、整数 `fontScale`。
- `NestedScrollSession` 已作为 internal 手势 session 状态容器接入；`PixelHostGestureRouter` 已迁成独立 internal class，`PixelHostView` 只保留事件入口和宿主桥接状态。
- 颜色与组件状态矩阵已有基础单测，`THEME_STATES` demo 已作为状态样式 gate；内置 `ThemeData` / token 层已移除，应用层自行组织主题对象并显式传入 `PixelColor`。
- `PerfBaselineTest` 默认只打印样本，不写 tracked baseline；只有 `REGEN_PERF_BASELINE=1` 时写盘；`PerfRegressionTest` 已提供只读阈值门禁。
- `PublicApiCoverageTest` 已检查公开 widget API 至少出现在 docs / demo / tests 中。
- 动画系统 Layer 1（核心）+ Layer 2（隐式 widget）+ Layer 3（`AnimatedBuilder` / `createTicker(maxFps=…)`）已落地；Sprite 帧动画 `AnimatedSprite` 也已落地。
- `PixelNavigator` / `PixelRoute` / `PixelNavigatorState` 已提供栈式导航、`of(context)` / `maybeOf(context)`、`maybePop()` / `PixelRoute.canPop` 拦截、route lifecycle、snapshot / Android Bundle restore 和 slide/fade transition。
- `Image` / `Sprite` / `AnimatedSprite`、`Line` / `Circle` / `Polygon` / `Path` / `CustomPaint` 已覆盖基础 bitmap 与图形原语；`PixelCanvas` 已支持 stroke width、rect/circle helper、linear/radial gradient 和 `SrcOver` / `Src` / `Clear` blend mode。
- Android PNG asset/resource loader、sprite sheet JSON loader、atlas trim/pivot/scale metadata、资源包级 `PixelResourceManifest` schema 和 per-owner `PixelResourceCache` 已落地；cache 已提供 lifecycle snapshot 统计 hit/miss/remove/clear。
- TextField 已支持 selection 高亮、IME composition 下划线、host frame loop 驱动的 cursor blink，并按 `selectionStart` 定位 caret。
- test-only `PixelTester` DSL 已能离屏 `pumpWidget`、坐标级 `tap` / `drag`、逐步 `startGesture().moveBy().up()/cancel()` 输入流、文本输入 / composition / submit、finder `nth`、失败 tree / target dump、`pumpFrame` 和基于 pending ticker/build/scroll 的 `pumpAndSettle`。
- 彩色系统已进一步收敛为单一 ARGB `PixelBuffer` 路径：公开 widget 直接接收 `PixelColor`，不再暴露 `PixelTone` / `PixelPalette` / `ThemeData` / `colorMode`。
- `pixel-demo` 已重构为单 `DemoActivity` + `DemoCatalog`，当前 catalog 注册 11 组 75 个 scene，首页是单页分组列表并用分类强调色区分 scene。

### 任务 #2：`ListViewSeparatedBuilder` lazy 版本

#### 状态

已新增 `ListViewSeparatedBuilder` lazy API，支持固定高度和显式估算高度，保留 `ListViewSeparated` eager API。

#### 动机

`ListViewSeparated` 当前是 eager：会一次性构造全部 item 和 separator。长列表使用它会有首屏构建成本风险。

`ListViewBuilder` 已有固定高度 lazy 路径，但只支持同一高度的 item。`ListViewSeparatedBuilder` 应该补齐“item 固定高度 + separator 固定高度”的 lazy 场景。

#### API 草案

```kotlin
public fun ListViewSeparatedBuilder(
    itemCount: Int,
    itemBuilder: (Int) -> Widget,
    separatorBuilder: (Int) -> Widget,
    state: PixelListState,
    controller: PixelListController,
    itemExtent: Int? = null,
    separatorExtent: Int? = null,
    estimatedItemExtent: Int? = null,
    estimatedSeparatorExtent: Int? = null,
    cacheExtent: Int = 1,
    key: Any? = null,
): Widget
```

#### 设计要求

- 保留现有 `ListViewSeparated` eager API，不做破坏性修改。
- item/separator 各自必须提供固定值或估算值；固定和估算模式可以混用。
- 内部需要正确计算交错虚拟行：
  - virtual index 偶数：item，真实 index = virtual / 2，高度 = `itemExtent`
  - virtual index 奇数：separator，真实 index = virtual / 2，高度 = `separatorExtent`
- 不能直接复用现有 `RenderLazyListViewport` 的 `itemExtent + spacing` 模型，除非先把它抽象成“按 virtual index 取 extent”的通用模型；否则 item/separator 不同高度会算错 offset。
- `state.itemTopOffsetsPx` 和 `state.itemHeightsPx` 仍应按真实 item 维度同步，保证 `scrollItemIntoView(state, itemIndex)` 定位真实 item，而不是 separator。

#### 文件

- `pixel-engine/src/main/kotlin/com/purride/pixelui/widgets/PixelWidgets.kt`
- `pixel-engine/src/main/kotlin/com/purride/pixelui/internal/widgets/scroll/ListWidgets.kt`
- `pixel-engine/src/main/kotlin/com/purride/pixelui/internal/render/pipeline/renderobjects/viewport/RenderScrollViewport.kt`
- `pixel-engine/src/test/kotlin/com/purride/pixelui/internal/render/pipeline/PipelineElementTreeRendererTest.kt`
- `pixel-engine/docs/组件目录.md`
- `pixel-demo/src/main/kotlin/com/purride/pixeldemo/catalog/DemoCatalog.kt`（scene 目录） 的 `PALETTE_GRID` 场景

#### 验收

- 1000 item 初始 render 只调用可见窗口 + cache 范围内的 `itemBuilder` / `separatorBuilder`。
- 点击 target 和 list target 仍被 viewport 裁剪。
- `scrollItemIntoView` 对真实 item index 生效。
- `ListViewSeparated` eager API 行为不变。
- demo `PALETTE_GRID` 改用新 builder。

### 任务 #3：性能回归阈值门禁

#### 当前事实

当前仓库已保留确定性性能性质回归（例如 lazy 窗口构建数量、远端 extent index
定位），但时间型 `PerfBaselineTest` / `PerfRegressionTest` 文件不在当前代码树中。
后续若恢复时间型 perf 门禁，必须保持只读默认，不得自动写 tracked baseline。

#### 状态

待恢复。当前不要在没有稳定本机/CI 基线的情况下新增硬时间阈值。

#### 设计要求

- baseline / regression 共享测量 helper，避免两套测量逻辑漂移。
- 默认永不写盘。
- baseline 文件不存在时 skip，并打印如何生成 baseline。
- JVM 不支持线程分配统计时 skip allocation 相关断言，不要 fail。
- 每项指标建议多轮采样取中位数，降低本机波动。
- 阈值先保守，避免 CI 噪声：
  - allocation：baseline * 1.5
  - render time：baseline * 2.0
  - blit：baseline * 2.0
  - rich text：baseline * 2.0

#### 验收

- 当前 baseline 下通过。
- 故意制造明显回归时失败信息要显示 baseline/current/threshold。
- 不修改 `perf-baseline.json`。

验证：

```bash
./gradlew :pixel-engine:testDebugUnitTest --no-daemon
```

### 任务 #C4：反向沉淀中级 widget（评估：当前无目标）

2026-05-25 评估：对 `app/` 全量 grep `PixelLeafRenderObjectWidget` /
`PixelSingleChildRenderObjectWidget` / `PixelMultiChildRenderObjectWidget`，
当前**只有一个候选**：[BatteryDividerWidget.kt](../../../app/src/main/kotlin/com/purride/pixellauncherv2/ui/widget/BatteryDividerWidget.kt)。

不沉淀的原因：

- 该 widget 做 1px 高的行 + 变宽 fill + 动画 accent 像素，所有这些都需要在
  同一个 `paint()` 内按当前 layout 宽度计算 `filledW = w * battery / 100`。
- 拆成 `Stack(Container(width=filledW) + Positioned(accent))` 反而每帧多分配
  3 个 widget 节点；并且父级必须先知道可用宽度才能算 filledW，破坏 Flutter
  风格"约束沿链下传"的常态。
- 这就是 `PixelLeafRenderObjectWidget` 公开扩展点的本意——业务自定义渲染原语。
  SDK 已经提供 [`Line`](../使用说明/组件目录.md#line) / [`Circle`](../使用说明/组件目录.md#circle) 覆盖通用形状；
  剩下的 1px-bar-with-animated-dot 是真正的 Launcher 业务语义。

下次新增 app 端 `PixelLeafRenderObjectWidget` 时再启动 C4 复评。

## 9. 工作建议

1. 每个任务先确认当前代码事实，再改。
2. 每个任务独立提交，不把功能、demo、文档、纯重构混在一起。
3. P1/P2 已有首轮实现，继续迭代前仍要按代码事实复核设计文档。
4. 改公开 API 必须同步 `README` 和 `docs/` 中对应文档。
5. 新增 widget 或公开 API 必须补 demo 和测试。
6. 不要在 `paint()` / hot path 中新增对象分配。
7. 不要从业务 app 反向污染 `pixel-engine`，engine 不应知道 Launcher 业务语义。
