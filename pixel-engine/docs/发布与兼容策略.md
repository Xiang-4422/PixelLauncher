# pixel-engine 发布与兼容策略

本文定义 Pixel Engine 从内部 `0.x` SDK 走向 `1.0` 后长期维护时的版本、兼容和迁移规则。
当前项目只有一个维护者，因此规则必须可执行、可检查，并且能通过 commit diff 直接审阅。
1.0 候选的逐项状态见 [1.0.0 发布清单](1.0.0发布清单.md)。

## 1. 版本阶段

### 0.x

`0.x` 是内部 SDK 阶段，source / binary 兼容是 best-effort。

- 新增 public API 允许进入 minor / snapshot 版本，但必须同步 KDoc、手册、demo 或测试。
- 删除、重命名、签名变化、默认值行为变化都算 breaking change。
- breaking change 必须写入根目录 `CHANGELOG.md`，并在同一提交更新 public / binary API baseline。
- patch 版本只允许 bug fix、文档、测试、性能或实现修复；除非修复严重错误，否则不做 breaking change。

### 1.0+

`1.0.0` 之后遵循 SemVer：

- MAJOR：包含 source / binary 不兼容变更，或稳定 public API 的关键行为破坏。
- MINOR：向后兼容的新 API、新组件、新能力，或新增弃用标记。
- PATCH：向后兼容的 bug fix、文档、测试、性能和实现修复。

稳定 public API 不随意破坏。需要破坏时，必须先经过弃用周期，除非继续保留会导致崩溃、数据损坏或无法修复的安全问题。

## 2. Public API 边界

以下内容纳入兼容承诺：

- `pixel-engine/api/pixel-engine.api` 中记录的 Kotlin public declarations。
- `pixel-engine/api/pixel-engine.binary-api` 中记录的 release binary API。
- `pixel-engine/docs/使用说明与API手册.md` 中承诺的主流程行为。
- `PixelHostBridge`、`PixelHostView`、`PixelTester`、controllers、theme、resource loader、公开 widget 的调用契约。

以下内容不纳入兼容承诺：

- `com.purride.pixelui.internal.*` 和内部 render / retained 实现。
- Launcher app 的业务组件和状态模型。
- 未写入 API baseline 的测试 helper、构建脚本内部任务细节。

### 实验 API

`@PixelExperimentalApi` 使用 `@RequiresOptIn(level = ERROR)` 和 BINARY retention。它表示调用方已明确
接受低层契约仍可能演进，不代表可以无记录地破坏：

- 新增实验 API 必须有中文 KDoc、行为测试、示例和 CHANGELOG；
- 实验 API 的不兼容变化只允许进入 minor/major，不进入 patch，并提供迁移说明；
- 稳定化前必须至少经过一个公开 minor 的消费者反馈，具备 source/binary baseline、独立消费者和行为证据；
- 稳定化时移除 opt-in 属于向后兼容变化；稳定后立即纳入完整 SemVer 承诺；
- 放弃实验 API 仍需先在一个 minor 标记弃用并给替代路径，除非存在安全或数据损坏紧急例外。

## 3. 弃用规则

`1.0.0` 之后，准备删除或替换 public API 时必须先弃用：

- 使用 Kotlin `@Deprecated` 标记，并给出清晰的 `message`。
- 有直接替代写法时提供 `ReplaceWith`。
- KDoc 写明弃用原因、替代 API 和最早移除版本。
- `CHANGELOG.md` 增加 `Deprecated` 小节。
- 如果在 `1.2.x` 标记弃用，`1.3.x` 仍必须保留；最早只能在 `1.4.0` 移除。

`0.x` 阶段不强制完整弃用周期，但能无成本保留兼容入口时优先保留，并在 changelog 写清迁移方式。

每个弃用声明都必须包含 `ReplaceWith`（确实不存在机械替代时在 KDoc 解释原因）、计划最早移除版本和
覆盖旧入口的兼容测试。删除发生时必须由 Metalava/JVM baseline diff、migration guide 和 major/minor
版本规则共同批准，不能只更新 baseline 让门禁变绿。

## 4. Migration Guide 规则

每个包含 breaking change 的版本必须同时提供 migration guide：

- 文档放在 `pixel-engine/docs/migrations/`。
- 文件名使用目标版本，例如 `1.4.0.md`。
- 必须说明影响范围、旧写法、新写法、迁移步骤和验证命令。
- 如果只有新增兼容 API，不需要 migration guide；在 `CHANGELOG.md` 记录即可。

模板见 `pixel-engine/docs/migrations/TEMPLATE.md`。

## 5. 发布检查清单

每个 SDK 发布提交至少检查：

- `pixel-engine/build.gradle.kts` 的 `version` 与发布目标一致。
- 当前发布状态已写入对应版本发布清单。
- `CHANGELOG.md` 有对应版本条目。
- 有 public API 变化时，已审阅并提交 `pixel-engine/api/` baseline diff。
- 有 breaking change 时，已补 migration guide。
- 有弃用时，KDoc、`@Deprecated` 和 changelog 同步。
- `pixel-engine/docs/使用说明与API手册.md` 和消费者示例不引用旧 API。
- 默认无设备门禁通过：

```bash
./tools/pixel-release-check.sh
```

功能性 Android Host 验收使用：

```bash
./tools/pixel-sdk-consumer-smoke.sh
./gradlew :pixel-engine:connectedDebugAndroidTest
```

性能基准、趋势、trace、Baseline Profile 与 soak 已移交后续独立性能 Goal，不属于当前 1.0 发布验收，
也不由默认发布门禁运行。

## 6. Breaking change 审批

稳定 API 的 source、binary、默认行为、持久状态格式和可观察时序变化都可能构成 breaking change。
变更必须在代码落地前记录影响面、替代方案、弃用时间线和版本级别；发布复核同时查看 Metalava、javap、
旧消费者二进制与行为测试。只有为阻止正在利用的安全问题、崩溃或数据损坏，才允许跳过正常弃用周期，
并按[安全修复与发布流程](security-release-process.md)发布新不可变版本。

## 7. 供应链与不可变发布

每个候选必须通过[发布元数据与供应链](supply-chain.md)：统一 POM、OpenPGP、四类 checksum、CycloneDX、
provenance、依赖锁定/验证、OSV 与 HTTP Maven 消费者矩阵。已经公开的 Maven 版本、tag 和 release notes
不得覆盖；发现问题时发布新的 patch/minor/major，并在旧版本文档中标注受影响范围。
