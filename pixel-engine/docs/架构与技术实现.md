# pixel-engine 架构与技术实现

本文描述 1.0 九 artifact 架构、技术实现和维护规则。如何使用 SDK 和查询组件 API，请读
[使用说明与 API 手册](使用说明与API手册.md)；最小依赖图和接入路径见 [SDK 首页](index.md)。
长期方向和阶段任务见 [长期规划](长期规划.md)。

## 1. 模块定位

pixel-engine 是像素风 Android UI SDK。它不依赖 Android View 树管理 UI，而是通过一个 `PixelHostView` 把 widget 树渲染到 ARGB `PixelBuffer`，再在 Android `Canvas` 上显示。

设计模型接近 Flutter：

- `Widget` 是不可变配置
- `Element` 是运行时实例和生命周期持有者
- `RenderObject` 负责 layout、paint 和 hit-test
- `PixelHostView` 是 Android 宿主

M7-1 已完成九个 artifact 的物理拆分：`pixel-core`、`pixel-runtime`、`pixel-widgets`、
`pixel-navigation`、`pixel-android`、`pixel-testing`、`pixel-debug`、可选 `pixel-compose` 和保持旧
单依赖体验的 `pixel-engine` 聚合坐标。目标所有权和无环依赖记录在
`config/artifact-ownership.json`，不得再把物理目录或 Kotlin package 当成实际发布边界。

最小 Host 消费路径是 core → runtime → widgets → navigation → android，不传递 testing、debug 或
compose。`pixel-compose` 在 M7-1 只冻结可选发布边界，尚未引入 `androidx.compose`；真正 Host
wrapper 归 M7-3。M7-2 的运行实例随 `pixel-android` 发布；legacy engine AAR 本体只保留已弃用的
兼容 marker，历史 testing/debug API 通过独立 artifact 的 POM 边保持可达，不在 engine AAR 中重复
打包 class。

`pixel-core` 因冻结的 `PixelBitmap.fromAndroidBitmap` JVM 描述符仍使用 Android Library 插件和
`android.jar` 编译，但发布运行时依赖只有 Kotlin stdlib，不引入 AndroidX UI、Lifecycle、Compose、
testing 或 debug artifact。新的平台能力必须进入 `pixel-android`，不能扩大这个兼容例外。

## 2. package 边界

### `com.purride.pixelcore`

底层像素能力层。

负责：

- `PixelBuffer`
- `PixelColor`
- `PixelBitmap`
- `PixelGridGeometry`
- `ScreenProfile`
- 字形包、字体引擎、文本栅格器
- sprite sheet、资源 manifest、资源缓存
- 轴向动画和 buffer 合成原语
- 渲染性能日志

禁止放入：

- Launcher 产品语义
- 页面模式
- Widget、布局、输入框、按钮等 UI 语义
- Android 系统服务读取

### `com.purride.pixelui`

UI runtime 与组件层。

负责：

- 公开 widget API
- retained build/runtime
- Element tree
- RenderObject pipeline
- 布局、文本、图形、图片、滚动、分页、输入、表单、导航、动画
- `PixelHostView` 和 Android 宿主桥接
- controller、状态辅助、调试组件

禁止放入：

- Launcher 产品状态
- 真实系统服务读取
- app 页面专属逻辑
- 旧 app 侧渲染 fallback

### `com.purride.pixelengine`

运行实例与聚合兼容 namespace。

- `PixelEngine`、`PixelEngineServices` 和 resource resolver 属于 `pixel-android`，因为默认帧源和
  Host 绑定由 Android adapter 提供；
- 已弃用的 `PixelEngineModule` 属于 legacy `pixel-engine` 聚合 artifact，只保留旧二进制入口；
- 该 split package 是冻结包名的受审兼容例外，精确所有权由 `artifact-ownership.json` 校验。

## 3. 组件准入边界

`pixel-engine` 是 SDK，不是 PixelLauncher 的组件库。新增公开组件前必须先判断它是不是通用 UI 能力，而不是某个产品页面抽出来的局部实现。

可以作为 engine 能力的组件通常满足：

- 名称是中性的，例如 `TextField`、`Slider`、`ListViewBuilder`、`PixelNavigator`
- 输入是通用参数，例如尺寸、颜色、状态、controller、回调、child / children
- 不读取 Android 系统服务，也不依赖 app repository / ViewModel
- 不知道 Home、Drawer、Settings、Idle、SMS、Diagnostics 等产品页面
- 可以在 `pixel-demo` 中用非 Launcher 场景独立展示

不应放进 engine 的组件包括：

- `LauncherHeader`、`LauncherSearchHeader`、`BatteryDividerWidget`
- `SettingsControls` 这类绑定 Launcher 设置项和主题 token 的组合控件
- `HomeScreen`、`DrawerScreen`、`IdleScreen`、`Sms*Screen`、`DiagnosticsScreen`
- `LauncherTheme`、`LauncherTextRasterizers`、`PixelFontCatalog` 等 app 侧主题/字体适配
- 通话、短信、闹钟、天气、Usage Access、App 启动等产品数据或系统能力接线

边界规则：

- engine 不得依赖 `com.purride.pixellauncherv2`
- engine 不得出现 PixelLauncher 页面模式或设置项枚举
- engine 默认样式只能是通用默认值，不得使用 Launcher 专属颜色、文案或布局密度
- app 可以通过 `com.purride.pixelui.advanced` 写定制 render object，但定制组件仍归 app 所有
- 只有当组件已经脱离产品语义、参数化充分、并有 demo / test 覆盖时，才允许提升到 engine

当前边界由两层门禁共同维护：`BoundaryOwnershipTest` 禁止 engine 引用 app 包；
`:pixel-engine:checkArtifactBoundaries` 读取 `config/artifact-ownership.json`，检查每个生产文件都有唯一
artifact owner、声明依赖图无环、实际项目 import 不越界、最小 artifact 不依赖 compose/debug/testing，
并只允许经过审阅的 Android import 与 split package 例外。

## 4. 三层模型

```text
Widget
  不可变配置对象：Text、Row、Column、ListView、TextField...
        |
        v
Element
  可变运行时树：生命周期、State、InheritedWidget、dirty rebuild
        |
        v
RenderObject
  layout + paint + hit-test，最终写入 PixelBuffer
```

### Widget 层

Widget 只携带配置，构造应保持廉价。`StatefulWidget` 把跨重建状态放入 `State`。普通页面代码应尽量停留在这一层。

### Element 层

Element 拥有 widget 生命周期。`BuildOwner` 收集脏 element，统一调度 rebuild。`InheritedWidget` / `InheritedNotifier` 通过 Element 树传播依赖。

### RenderObject 层

RenderObject 处理底层几何和绘制。`RenderBox` 子类实现 layout 和 paint，输出写入 `PixelBuffer`。自定义底层组件时通过 `com.purride.pixelui.advanced` 暴露的 alias 进入。

## 5. 渲染主链路

```text
PixelHostView.setContent(...)
        |
        v
RootWidgetProvider
        |
        v
PixelUiRuntime.render(newWidget)
        |
        v
BuildOwner.updateRootWidget(newWidget)
        |
        v
BuildOwner.buildScope()
        |
        v
PipelineOwner.render()
        |
        v
PixelBuffer
        |
        v
PixelHostView.onDraw(Canvas)
```

一次 frame 的职责边界固定如下：

1. `PixelUiRuntime.render(root, logicalWidth, logicalHeight)` 是宿主入口。
2. `RetainedBuildRuntime.resolveElementTree` 驱动 `BuildOwner.renderPass`：先 reconcile 根 widget，再排空 dirty build 队列。render pass 内产生的 `markNeedsBuild` 会在本帧处理完，不额外请求下一帧。
3. `PipelineElementTreeRenderer` 从 retained element tree 中解析 `RenderBox` 根，并交给 `PipelineOwner.attachRoot`。
4. `PipelineOwner.render` 先判断缓存：当 layout/paint 都不脏且逻辑尺寸不变时，复用上一帧 `PixelRenderResult`。
5. 需要重绘时创建 `PixelRenderSession`，从 `PixelBufferPool` 获取当前帧 buffer。`needsLayout` 为 true 时先用宿主逻辑尺寸约束执行 layout。
6. paint 阶段从根 render object 写入 `PixelBuffer`，随后收集 click / pager / list / scrollbar / refresh / text input / slider target 和 semantics target。
7. `PixelRenderResult` 是本帧提交产物，包含 buffer、命中目标和 semantics；Android 侧由 `PixelHostView.onDraw(Canvas)` 把 buffer 画到宿主 Canvas。
8. 只有完整帧诊断显式开启时，platform-neutral `PixelFramePhaseSink` 才把 build/layout/paint 和
   dirty/cache/pixel 计数传到 Host；Host 另外测量 buffer submit 与 exclusive Android draw，
   最终固化为 `PixelHostFrameDiagnostics`。

当前策略是整帧提交，先依赖 dirty layout/paint 标记和 buffer 复用控制成本；dirty region / partial repaint 只在真实瓶颈出现后引入。

完整帧计时不重叠：`paintNanos` 只包含 engine 写逻辑 buffer 和导出 targets，
`bufferSubmitNanos` 才包含 `drawBuffer` 的 bitmap `setPixels`/`drawBitmap` 或 gap 逐格 Canvas
调用；`androidDrawNanos` 排除 submit，覆盖 `View.draw`、背景清理和 accessibility publication。
`totalFrameNanos` 从 Host `onDraw` 入口到 ART terminal sample，snapshot 构造和消费者 callback
在统计边界之外。这样人工制造任一阶段延迟时不会因为嵌套计时而总被 Android draw 吞掉。

### Semantics tree 与 Android virtual nodes

Semantics 与像素 buffer 同帧提交，但不把 Android 类型引入 widget/render 公共层：

1. 每个会导出语义的 retained `RenderObject` 为本地语义槽位分配单调、进程唯一的
   `PixelSemanticsNode.id`。节点更新和 keyed sibling 重排不替换这个 ID。
2. `RenderSemantics` 先隔离收集后代，再应用普通 parent/child、`mergeDescendants` 或
   `excludeDescendants` 策略。flat render target list 中仍携带 `parentId`，因此提交结果可重建
   完整虚拟树。
3. 不可执行的 `PixelSemanticsNode` 只保存属性和 action descriptor；真实 callback 留在内部
   `PixelSemanticsTarget`。测试和 Android 都按 stable ID 定位 target，禁止按 bounds 中点二次
   hit-test。
4. 每个 `PixelHostView` 拥有独立 `PixelHostAccessibilityNodeProvider`。Provider 把 semantic
   ID 映射为本 Host 内单调递增、不复用的 `Int` virtual ID，保存前后两帧快照、accessibility
   focus 和 touch-exploration hover owner。
5. Android node 查询按 `parentId` 生成真实 parent/children，映射 class、checked/selected、
   range、collection、live-region 和 typed actions；frame diff 与 action 路径发送带 virtual
   source 的内容、焦点、选择、文本、滚动和窗口事件。
6. retained detach 可以保留 semantic identity；pause/stop 时 action 受 Host interactive 状态
   gating，destroy 才清空 ID registry、focus、hover 和旧快照。两个 Host 不共享 virtual ID 或
   focus owner。

`PixelSemanticsNode.id` 和 Android virtual ID 都是运行期身份，不是持久化 key。业务若需要在
重建或动态重排后保留逻辑节点，仍必须给 widget/`Semantics` 提供稳定业务 `key`。完整使用与
迁移契约见 `docs/migrations/1.0.0-accessibility-semantics.md`。

`PixelHostView` 同时负责：

- Android `View` 生命周期
- touch/key 输入转发
- IME 桥接
- window insets / view insets 同步
- host 级背景、格栅色、像素形状和缩放
- frame scheduler
- inspector / frame stats

Host 把环境更新组织成一个原子快照，而不是让 direction、motion、density、inset 和 display feature
分别穿过 widget 树。`AndroidPixelHostCapabilitiesSource` 在主线程读取 Configuration、display 与
contrast；`HostRootWidget` 从同一份 `HostCapabilitiesData` 派生 `Directionality`、
`PixelMotionScope`、`MediaQuery` 和 `PixelAdaptiveEnvironment`。distinct snapshot 只通知真正依赖
对应 inherited scope 的 Element。

物理窗口映射分为两层：`PixelHostProfilePolicy` 先确定逻辑行列，`PixelViewportPolicy` 再确定
Contain/Cover、Integer/Fractional 和 alignment。`PixelGridGeometryResolver` 是 paint、pointer
inverse、Accessibility bounds 和 inset projection 的唯一几何来源。Android system bars、IME 和
cutout 先保留原始物理数据；resize、profile、density 或 viewport 变化后统一重投影，避免逻辑 inset
和画面使用不同世代的 geometry。

`HostRootWidget` 同帧注入 `PixelAdaptiveLayoutData`，其中物理 px/dp size class、逻辑尺寸、
MediaQuery inset 和 capability display feature 来自同一 Host frame。`AdaptiveBuilder` 只是 inherited
依赖边界，不拥有业务 State；retained key/type/slot 稳定时，环境切换不会主动替换 State、FocusNode、
滚动控制器、TextField selection 或 route entry。

对外迁移契约见
[自适应 Host 与 Viewport 迁移指南](migrations/1.0.0-adaptive-host-viewport.md)。

M5-3 的最终集成不另建 Demo-only 环境模型。`Adaptive & Localization` 场景直接修改
`PixelHostView.capabilitiesOverride`，由 Host 根重新派生 Directionality、MotionScope、MediaQuery、
PixelAdaptiveEnvironment 和高对比度 theme；Stateful scene、TextField controller/focus node、外层
scroll state 与 `PixelMultiStackNavigatorController` 保持原 identity。场景销毁时恢复原 Host policy，
避免验收 override 泄漏到其它 Demo。

确定性回归使用七个只读场景：English/Chinese LTR 1×、Arabic RTL 1×、LTR 2× textScale、
high contrast、compact hinge、small-window IME。semantic snapshot 固定本地化 label、UTF-16
selection、geometry、window class、IME/feature 值；ASCII pixel golden 固定 RTL child 视觉顺序、
textScale 尺寸、高对比度 surface 与 SafeArea/IME 裁切。测试可以输出 `build/reports` 候选用于
审阅，但生产基线目录没有运行时写入或环境变量更新分支。

## 6. Host 接入

推荐入口是 `createPixelHostSetup(...)`。

它会创建或接收一个 `PixelHostView`，连接默认 `PixelTextInputBridge`，并返回包含宿主视图和隐藏输入框的 `FrameLayout`。

M7-2 在 Host 外增加不可变的 `PixelEngine` 所有权边界：

```text
PixelEngine
  ├─ clock / error reporter / logger
  ├─ frame scheduler / ticker provider factory
  ├─ resource resolver / per-engine cache
  ├─ HostCapabilitiesData override
  ├─ PixelHostCapabilitySet
  └─ explicit theme override
          |
          v
PixelHostView.bindEngine(engine)
          |
          v
HostRootWidget -> theme/capability inherited scopes -> retained runtime
```

Host render coordinator 动态读取当前 Engine 的 clock/reporter/logger。frame scheduler 或 ticker
factory 变化时，Host 重建自己的 `PixelHostFrameScope`；资源 cache、resolver 和 Host capability
继续由 Engine 拥有。多个 Host 可以显式共享一个 Engine，但 ticker provider、focus、retained tree、
accessibility virtual ID 和 frame diagnostics 始终是 Host 私有状态。

Engine 的聚焦 capability 以 `PixelHostCapabilitySet` 发布到 widget 树，`PixelHostServices.of(context)`
读取最近集合。合并优先级是 Engine-first，冻结的 `PixelHostBridge` 只补缺。IME、clipboard、haptic、
back、accessibility、saved state 与 system action 彼此独立；缺失返回 `Unsupported`，实现异常转为
`Failed`。新 action 使用封闭 Kotlin 类型，只有 legacy adapter 才映射到旧字符串协议。

`PixelUiRuntime` 使用 Engine clock 生成 `PixelErrorEvent.timestampNanos`，并在 build、render、
boundary recovery 与 fallback failure 的结果确定后上报。Reporter/logger 的二次失败被隔离；无边界
原异常仍按历史契约抛出。完整外部契约见
[PixelEngine 实例与服务迁移指南](migrations/1.0.0-engine-services.md)。

M7-3 的 `pixel-compose` 是单向 AndroidView adapter，不是第二套渲染后端：

```text
Compose composition
  -> PixelHost(engine, content = () -> Widget)
  -> PixelComposeHostContainer
  -> PixelHostSetup(root + PixelHostView + hidden editor)
  -> retained Pixel Widget / RenderObject pipeline
```

AndroidView 的 ViewTree owners 驱动现有 `PixelHostLifecycleCoordinator`；容器只显式转发
WindowInsets，并在 `onRelease` 调用 setup.dispose。density 来自同一 Android Context/configuration，
焦点与 IME 仍由真实 Host/隐藏 EditText 处理，virtual accessibility nodes 继续挂在 AndroidView 子树。
saved state 由有界 `rememberSaveable` capability 补入 Engine，`withHostServicesFallback` 保证应用已有
capability 优先并共享原 cache/clock/scheduler 引用。任意 Composable 不能成为 retained pixel tree
节点；反向嵌入会形成两套布局、语义和生命周期 owner，1.0 明确不支持。详见
[Compose Host 互操作迁移指南](migrations/1.0.0-compose-host.md)。

### Attachment 与 owner lifecycle

Host 不再用 View detach 代替完整生命周期。`PixelHostLifecycleCoordinator` 同时维护：

- attachment 轴：`Detached` / `Attached`；
- owner 轴：`Unmanaged`、`Initialized`、`Started`、`Resumed`、`Paused`、`Stopped`、
  `Destroyed`。

只有 attached + unmanaged/resumed 会产生 `isInteractive=true`。状态变化由同一个 diagnostics
回调同步到各子系统：

- `PixelHostFrameScope.resume/pause` 控制 ticker active time 和上游 frame；
- `PixelHostRenderCoordinator.setLifecycleActive` gate 动态 visual update；
- 非 interactive 时取消手势、predictive back preview 和 pending click，并隐藏 IME；
- destroyed 时一次性释放平台 back、输入、frame scope、retained/render tree 和缓存。

`onAttachedToWindow` 通过 `findViewTreeLifecycleOwner()` 自动发现 owner，显式
`bindLifecycleOwner` 的优先级更高。`onDetachedFromWindow` 只推进 attachment 轴，不释放 retained
tree。owner destroy 或显式 `destroy` 才进入终态；旧 `dispose()` 只是 destroy 的兼容别名。

协调器把重复、乱序和终态后的事件记入 `ignoredTransitionCount`，使 attach/detach 和 owner
切换可以被测试，而不靠持有真实 owner 引用的调试对象。

### Host-owned frame/ticker scope

每个 `PixelHostView` 独占一个 `PixelHostFrameScope`。scope 本身实现
`PixelCancellableFrameScheduler`，把一个上游 `PixelFrameScheduler` 复用给：

- 一次性、可取消的 frame callback；
- 重复 frame listener；
- 一个 Host 私有 `PixelTickerProvider`。

上游同时最多保留一个 pending callback。支持 cancellation capability 的 Choreographer 和
`ManualFrameScheduler` 会物理移除 callback；只实现旧 `PixelFrameScheduler` 的第三方实现由 guarded
callback 提供逻辑取消，因此 `scheduleFrame(...): Unit` 的旧 ABI 不需要变化。

active time 只累加两个 active source frame 之间的正向 delta。pause 会取消上游 callback 并保留
逻辑 demand；resume 的第一帧只重新锚定原始 timestamp，后续才继续累加。于是后台停留时长不会
进入 `PixelTicker` elapsed time。

scope dispose 会终结 provider，并清空 callback 和 listener。dispatch 每次执行前重新检查 scope
状态，所以某个 ticker 在当前 frame 内触发 destroy 后，同一 snapshot 中后续 ticker/listener 不会
继续运行。

`PixelHostView.frameScheduler` 的 setter 会创建新 scope，让它遵循当前 lifecycle，然后 dispose 旧
scope。它不迁移动画；`tickerProvider` 是动态 getter，换源后的消费者必须读取新 provider。每个
Host 即使共享同一上游 scheduler，也不共享 scope、active time 或 diagnostics。

消费者迁移与 Fragment/非 owner 接线见
[Host 生命周期与调度迁移指南](migrations/1.0.0-host-lifecycle.md)。

## 7. 子系统概览

### 文本系统

`Text`、`RichText`、`TextField` 共享 paragraph layout 支持。当前能力包括：

- TextField 使用 Unicode 17.0.0 extended grapheme 进行移动、删除、selection 和 composition
- `maxLines`
- `CLIP` / `ELLIPSIS`
- span 样式切换
- 文本对齐
- 多行 TextField caret / selection / composition
- selection handle 和平台 Copy / Cut / Paste / Select all 菜单

文本索引分成三个不能混用的层级：公开 selection/composition/Accessibility 是 Android UTF-16
offset；字符解码和后续 glyph key 使用 Unicode code point；用户可见编辑使用 extended grapheme
cluster。`PixelGraphemeBoundaryMap` 由 engine-owned Unicode 17.0.0 数据驱动，不调用设备 ICU，
因此 API 24 与 API 37 的编辑边界一致，也不会改写 NFC/NFD。

Android 默认桥接通过 `PixelEngineTextInputView` 包装真实 `EditText` InputConnection。平台仍负责
普通 IME 协议，引擎层负责在 commit/composition/selection/delete、硬件编辑键和 API 34 replace
前后规范化边界；connection generation 隔离目标切换，batch arbitration 保证 Host rebind 与平台
未发布编辑不会互相覆盖。该实现保持 internal，稳定 API 只暴露 `EditText`、
`PixelTextEditingHostBridge` 和 `PixelTextEditingValue`。

Paragraph 以同一份 `PixelGraphemeBoundaryMap` 构造 styled cluster，硬换行、soft wrap、ellipsis、
letter spacing、caret、hit test、selection/composition rect 和 Accessibility character bounds 都
消费该 cluster source range。每条物理行由 engine-owned Unicode 17.0.0/UAX #9 revision 51
resolver 生成 embedding level 和逻辑↔视觉映射；selection start/end 的 Bidi affinity、TextField
handle 和 pointer 命中不会各自重新估算几何。该实现不改写 backing String，公开索引继续是 UTF-16。

逻辑 grapheme 支持、UBA 视觉排序和真实字形 shaping 是三个独立能力。1.0 提供前两项和确定性的
unsupported-cluster fallback，不把它解释为内置 Arabic/Indic contextual shaping、彩色 emoji 或
全部 ZWJ 字形资产支持。

字体链路：

- `PixelTextRasterizer`
- `PixelFontEngine`
- `PixelGlyphPack`
- `PixelGlyphPackAssetLoader`
- `PixelBitmapFont`

字体 fallback 顺序由调用方显式组装：

1. `PixelGlyphPackAssetLoader` 只负责从 Android assets 加载 `manifest.json` 和 `glyphs.bin`，不参与字体选择。
2. `BitmapGlyphSource` 只消费 `cellHeight` 与当前 `GlyphStyle` 匹配的字形包，并按 pack 顺序用完整 Unicode scalar `Int` 查找，supplementary key 不会窄化为 `Char`。
3. `CompositeGlyphProvider` 按 source 顺序查找 scalar，全部缺字时返回一个可见缺字方框；空白和控制 scalar 只保留 advance。
4. `PixelFontEngine` 以 code point 迭代 backing UTF-16，并按完整 scalar 和 style 建立 cache key；冻结的 `Char` SPI 通过 default method 保持旧消费者二进制兼容。
5. Paragraph 通过 `PixelClusterTextRasterizer` 询问多 code-point cluster 的原子支持；不支持的非 ignorable cluster 只替换成一个 U+FFFD，纯 default-ignorable cluster 保持零宽且不绘制。
6. UI 层最终通过 `PixelTextRasterizer` 接入字体；未显式提供时使用 `PixelBitmapFont.Default`，保证零资产依赖也能渲染文本。

Bidi 数据由 `tools/generate_unicode_bidi_data.py` 从固定 checksum 的 Unicode 17 输入生成；
`--check` 在不写文件的情况下验证 tracked input 与 production table 一致。完整 `BidiTest.txt` 和
`BidiCharacterTest.txt` 对 resolver 做 conformance，设备运行时不参与 Unicode 版本选择。

每个 `PixelUiRuntime` 拥有独立的 focus owner、root scope 和 primary focus；Host、离屏 runtime
与 `PixelTester` 不再通过进程全局焦点转发输入。scope 记录父子关系，因此 modal owner 可以拒绝
背景节点的 `requestFocus`，同时允许 Dialog 内部的 `FocusTraversalGroup` 和 TextField 子 scope。

标准控件的 `AutomaticFocusAction` 为每个叶控件认领一个独立 FocusNode；一个祖先 Focus 包含多个
控件时，后续控件会创建自己的 retained node，避免 handler、disabled gate 和 IME target 相互覆盖。
FocusNode 另有父节点链：owner 先从当前节点向祖先执行应用 `onKeyEvent`，全部拒绝后才执行组件
默认动作，再进入遍历。这使页面级快捷键具有稳定优先级，同时不把多个语义控件折叠成一个 tab stop。

Android 键盘、DPAD、游戏手柄按钮/摇杆和 `PixelTester` 最终都生成 `PixelKeyEvent` 并交给当前
runtime owner；Switch Access 通过同一 Semantics callback 进入业务动作。TextField 聚焦时，字符、
物理键盘方向键和 Enter 留给 editor，Tab/Escape 以及 DPAD/游戏手柄导航键才转给 owner；IME
`NEXT` 同样只在所属 Host 内触发 Tab。

Dialog、Menu 和 Popover 通过 modal token 栈管理逻辑 presentation。激活时捕获 opener，优先
使用 autofocus，否则选择首个 enabled 节点进入弹层；逻辑关闭时立即弹出 token 并
恢复 opener，退出动画不延迟该过程。嵌套 modal 使用 LIFO token，Escape/Back 只交给最上层。

背景隔离不依赖 RenderFlex/RenderStack 的 target 收集顺序。每个 active modal render boundary
持有单调 activation token；一帧所有 target 收集完成后，pipeline 从 target `source` 的 render
ancestry 选择最大 token，只保留属于该 boundary 的 click、scroll、TextField、Slider、hit-test 和
semantics target。OverlayHost 的每个 presentation 还携带 canonical route order：属于 active modal
的目标与顺序更高 route 的目标会保留，背景和更低 route 被过滤，避免“上层 System 像素可见但
不可点”。私有 modal marker 保证无语义后代的空弹层也能隔离背景，最终结果不会把 marker暴露给
Android 或测试。`active=false` 的 retained exit subtree 不再产生 token，只继续 paint。

生产级 Overlay 在此基础上分为两条互补路径：

- `PixelOverlayController` 持有 `PixelPopupRoute<R>` 的逻辑 entry，以显式 layer 和单调 insertion
  sequence 形成唯一总序。逻辑 close 立即把 entry 移出 Back/focus/interaction 栈；Host 保留 keyed
  visual wrapper 到退出和 Element dispose 完成，再向 controller acknowledgement。controller 以逻辑
  close FIFO 排队 outcome，只有队首已被所有 Host 卸载时才 delivery，因而不同 motion 时长不会
  重排结果，也不会让回调观察到半卸载子树。
- 声明式 `Popover` 使用双分支 render portal。anchor 分支独占普通布局尺寸；presentation 分支按
  MediaQuery Host viewport 布局，在 base tree paint 时登记到 `RenderOverlayLayerRegistry`。若较高
  root-Stack sibling/route 尚未绘制，它也会登记为后续根平面；`PipelineOwner` 依序重放 lifted
  presentation 与这些较高平面，并以同一顺序收集 hit-test 和所有 target/semantics，避免低 route
  portal 在最终追加绘制时越过高 route。位于 scratch context 的较高 sibling 会先绘入透明捕获面，
  携带原 clip extent、group opacity 与全局 rational transform 再进入根平面；原 retained subtree
  继续负责 target/semantics，plane rank 统一修正它们与 raw hit 的顺序。`PaintContext`
  在 opacity、clip、scroll、pager、slidable 和 fitted scratch buffer 间组合平移/缩放映射，所以
  anchor 的全局 bounds 与真实像素一致，而 presentation 不受祖先局部裁切。

Dialog/BottomSheet 使用共享安全视口 render primitive：stable `viewPadding` 与 transient
`viewInsets` 每边取最大值，child 在剩余矩形内测量并 center/bottom-center 对齐。该 render object
用相同矩形裁切 paint、hit-test、scroll/input targets 和 semantics，避免“视觉已裁切但隐藏按钮仍可
点击”的分叉。Toast/Snackbar 队列的 dwell time 由 Host active-time ticker 驱动，与视觉
reduce-motion/animator scale 分离，dispose 会同步注销 listener 和 ticker。

Retained teardown 使用失败聚合而不是首个异常即中断：Element 先快照全部 child，逐个 unmount，
再清 slot、State attachment、焦点/监听与 dirty schedule；MultiChild/Root slot 即使遇到用户
`dispose` 或 overlay outcome callback 异常也会提交终态。清理完成后首个异常携带 suppressed
异常交回调用方，因此错误可见但不会留下半卸载树。`ChangeNotifier` 同样先对 listener 快照完成
全量 fan-out；Overlay controller 再继续 drain ready outcome，所以单个业务 observer 失败不能阻断
Host 重建、队列 ticker 注销或 focus/scheduler 清理。

完整默认行为和非模态 Popover 配置见
[模态焦点与背景隔离迁移](migrations/1.0.0-modal-focus.md)。

### 导航

导航能力由 `PixelNavigator` 提供，M2-1 的内部栈单位是独立
`PixelRouteEntry<A, R>`，不再把可复用的 route / destination 定义本身当作栈位置。

#### Entry 模型与所有权

每次 push 都由 `PixelNavigatorState` 分配一个 navigator 内单调递增的
`PixelRouteEntryId`，并创建以下 entry 私有对象：

- typed `arguments`
- `PixelRouteStateBucket`
- `PixelRouteResultChannel<R>`
- `PixelRouteLifecycleState`
- 创建时冻结的 `maintainState`

`PixelRouteDestination<A, R>` 只描述 builder、transition、pop policy 和 lifecycle
callback，可以安全地被多次请求。相同 destination，甚至相同 legacy `PixelRoute` 对象重复
push，也不会复用 entry ID、bucket、channel 或 lifecycle。`PixelNavigatorState.entries` 是
真实 entry 栈；`stack` / `currentRoute` 是为旧 API 保留的 `PixelRoute` 投影。

typed builder 通过 `PixelRouteEntryScope<A, R>` 访问当前 entry。scope 保留 entry 身份，所有
complete、cancel、replace 操作都回到 owner 校验，防止已经离栈的 stale scope 修改新 entry。
`replaceWith(PixelRouteRequest<NextA, R>)` 可以改变 replacement 参数类型，但故意固定结果类型
`R`；旧 entry 和 replacement 的调用协议因此在编译期一致。

`PixelRouteStateBucket` 使用 `IdentityHashMap<PixelRouteStateKey<*>, Any?>`。key 的诊断
`name` 不参与相等性，只有同一个 key 对象才能访问同一值。兼容的 route scroll snapshot 也
收敛进 entry 自己的 bucket，因此重复 route 不再共享滚动恢复状态。

#### 生命周期状态机

状态先提交，随后才调用 destination callback。callback 抛错会生成结构化 failure，但不能
回滚已提交状态，也不能阻断其他 entry 的清理。

| 状态变化 | 原因 | 实现约束 |
|---|---|---|
| `Created -> Active` | root、push、replacement 成为前台 | 恢复 bucket retention，然后调用 `onEnter` |
| `Created -> Inactive` | 旧版 stack restore 中的非前台 entry | 初始化状态，不伪造 enter / exit callback |
| `Active -> Inactive` | 被新 entry 覆盖 | 非 maintained entry 同步清 bucket 并暂停 retention，再调用 `onExit` |
| `Inactive -> Active` | 下层 entry 再次成为前台 | 恢复 retention，再调用 `onEnter` |
| `Active -> Removing` | pop / cancel / replace / remove / clear / host dispose | 状态先离栈，再调用一次 `onExit` |
| `Inactive -> Removing` | remove / clear / reset / host dispose | 不重复调用 `onExit` |
| `Removing -> Disposed` | 转场 settle 或同步 finalize | 清空并永久关闭 bucket，调用一次 `onDispose` |

所有转换方法都有 exactly-once guard。被打断的转场会在新 mutation 之前同步 settle；旧动画
listener 即使晚到，也因为 transition ID 不再匹配而不能重复 dispose。result channel 同样只能
从 `Pending` 终结一次。

#### Retained entry host

Navigator widget 始终按 entry ID 给真实 route host 分配稳定 key，而不是使用 route name 或
stack index。这样删除中间 entry、重复 destination 和 replacement 都不会把一个 Stateful
subtree 错配给另一个 entry。

`maintainState=true` 时，inactive entry 的真实 subtree 继续挂载；其 wrapper 把 opacity 设为
0，同时关闭 child layout、hit-test 和 widget collection / finder 暴露。后台 entry 因此保留
完全相同的 State 实例，却不消耗子树 layout/paint、不响应输入，也不会被页面 finder 当作当前内容。

`maintainState=false` 时，entry 在离场阶段仍可为转场短暂存在；转场 settle 后从 presentation
entries 移除并卸载 subtree。进入 inactive 时 bucket 已清空且禁止 late disposal write；再次
active 时会重新挂载一个全新的 Stateful subtree。所有 entry 在 `Disposed` 时无条件清空
bucket，与 maintain policy 无关。

自定义 `PixelRouteTransitionBuilder` 使用带 transition ID 后缀的 `outgoing` / `incoming`
presentation widget。它们是转场展示副本，不承担长期 State 所有权。真实 maintained entry
host 继续在稳定 keyed 位置挂载，只是在 custom transition 期间隐藏；转场结束后展示副本被
释放，真实 incoming host 恢复可见。

#### Finalization 与结果顺序

离栈 mutation 只把 entry 放入 insertion-ordered pending finalization queue。真正 settle 分成
两个阶段：先依次 dispose 队列内所有 entry，再依次 resolve 并 drain result callback。这个
分段保证 callback 重入时观察到的是已经完成清理的 stack。

| 操作 | finalization 顺序 | outcome |
|---|---|---|
| typed complete | 当前 entry 转场结束后 dispose，再投递 | `Success(value)`，允许 value 为 null |
| legacy pop | 当前 entry dispose 后投递 | 为兼容旧行为，`pop()` 等价于 `Success(null)`；`pop(value)` 为 `Success(value)` |
| typed cancel | 当前或指定 entry dispose 后投递 | 默认 `Cancelled(Explicit)` |
| typed replace | outgoing dispose；replacement 独立运行 | outgoing 为 `Cancelled(Replaced)` |
| remove inactive | 无视觉转场，同步 dispose 后投递 | `Cancelled(Removed)` |
| remove active | 可等待离场转场 | `Cancelled(Removed)` |
| clear | root 以上 entry bottom-to-top 全部 dispose，随后同序投递 | `Cancelled(Cleared)` |
| host dispose | 保留已有 finalization 顺序，再把剩余 stack top-to-bottom 入队；全部 dispose 后投递 | `Cancelled(NavigatorDisposed)` |
| restore / deep-link reset | 旧 stack entry 进入统一 finalization | `Cancelled(StackReset)` |

legacy `push(route, onResult)` 适配层把 `Success(value)` 映射为 value，把任何
`Cancelled(reason)` 映射为 null。legacy `replace(route)` 还保留原有 stack-slot callback
语义：只转移尚未投递的 callback；旧 channel 自身终结为 `Cancelled(Replaced)`，replacement
仍拥有新的 entry、bucket 与 channel。typed replace 不做 callback 转移。

pop 与 typed complete 会执行 destination 的 `canPop(entry)`，拒绝或 callback 异常时不提交
mutation。cancel、remove、replace、clear 是显式栈管理操作，不走 canPop policy。

#### Observer、failure 与快照边界

`PixelNavigationObserver` 接收不可变、带单 Navigator 单调 sequence 的 Started / Completed /
Failed 事件。observer、lifecycle 和 result callback 异常彼此隔离；最近一次结构化失败保存在
`lastFailure`，供诊断而不是控制流使用。

`inspectionSnapshot()` 复制 entry ID、destination ID、lifecycle、result state、maintain policy、
state key name、current entry、transition 和 failure。它不保留 arguments 或 widget，且只保证
当前进程内测试和 inspection 的确定性；它不是持久化 DTO。

旧 `PixelNavigatorSnapshot(routeNames)`、Bundle helper、字符串 route registry 和 legacy deep
link resolver 继续存在，只会重建新的 legacy entry。typed 持久化不复用该 DTO，也不把
inspection snapshot 或 destination ID 单独当作恢复协议。

#### 版本化恢复流水线

`PixelNavigatorSnapshotCodec` 把持久化拆成四层：

1. `PixelRouteSnapshotRegistry` 以 destination ID 建立显式 allowlist；编码当前进程时还要求
   adapter 与 entry 持有同一个 destination 实例。
2. `PixelRoutePayloadCodec<A>` 负责编码参数，并按 payload schema 显式迁移。引擎不做反射或
   `Serializable` fallback。
3. `PixelRouteSnapshotAdapter<A, R>` 只选择允许恢复的 route-local state；普通 bucket 值不会
   自动落盘。
4. outer codec 写入 `PXNV` magic、schema、payload length 和 CRC32；decode 在调用 destination
   代码前执行 entry 数、字符串、参数、state value、aggregate bytes、重复 ID 和 current entry
   校验。

当前 outer schema 为 2，并支持没有 current ID / local state 的 schema 1。任一步返回 Rejected
都会保留 live stack。decode 成功得到一次性 `PixelNavigatorRestorePlan`；plan 内的 decoded 参数
和 detached bucket 不公开，且只能被一个 Navigator claim。安装时保留原 entry ID，并把 allocator
推进到最大恢复 ID。

pending result callback、Widget/State、ticker 和 listener 不进入 snapshot。它们属于旧进程调用
栈和 runtime 所有权，跨进程伪恢复会制造悬挂引用。

#### 嵌套与多返回栈

`PixelNestedNavigator` 为 inner tree 持有独立 `PixelBackDispatcher`，只向 parent dispatcher
注册一个 bridge；传入的 parent entry 不处于 Active 时 bridge 完全离栈。

`PixelMultiStackNavigator` 用稳定 `(controller identity, stack ID)` key 同时挂载所有 child
Navigator。inactive child 外层 opacity 为 0，从 render target、hit-test、semantics 和 finder
隔离，但 Element/State 与 route history 保留。每个 child 有私有 back dispatcher，outer
controller 只把离散或 predictive session 转发给开始时 active 的 stack。切 tab 会先取消旧
session，避免 progress 泄漏到新 tab。

`PixelTypedNavigatorStack` 通过 typed root 让每个 child 可持久化。多栈 outer Bundle schema 保存
active stack 和按 index 编码的 child bytes；恢复前要求 stack ID 集合完全匹配、全部 registry
存在，并先 decode 所有 child plan，再进入安装阶段。一个损坏 tab 不会被静默丢弃。

#### Typed Deep Link

`PixelTypedDeepLinkRoute<A, R>` 把 matcher、`PixelDeepLinkArgumentDecoder<A>` 与 destination 的
泛型配对。matcher 先声明 URI 所有权，decoder 再返回 typed arguments 或 Missing / Invalid
结构化拒绝；命中后失败不会 fall through 到另一 destination。成功 push / replace 使用
`PixelNavigationAction.DeepLink` 发送 observer 事件。多栈定向只有成功后才改变 active stack。

#### Predictive Back 状态机

`PixelBackDispatcher` 在 start 时从顶层向下选择一个 handler，并把同一 session 的 progress、
cancel 和 commit 锁定到它。顶层离散 overlay 会阻止底层 Navigator 提前预览。disabled handler
不注册，因此 root 页面不会让 Host 无条件接管系统返回。

`PixelHostView` 的平台 adapter 在 attach 后按需注册：API 33 使用 `OnBackInvokedCallback`，API
34+ 使用 `OnBackAnimationCallback`。Host session 保留“focused input -> widget dispatcher -> app
fallback”的优先级；input 只在 commit 清焦点，cancel 无副作用。

Navigator start 时创建不改 stack 的 Pop presentation record，最新 `0f..1f` progress 直接进入
既有 transition visual / custom builder。cancel 只删除 preview。commit 才执行生命周期和
finalization，typed channel 终结为 `Cancelled(Back)`，且不会再启动第二条定时动画。若期间发生
push/replace/remove，preview 标记为 interrupted，迟到 commit 返回 false，不会误删新页面。

### 主题与组件状态

`PixelTheme` 同时保存 legacy `PixelThemeData` 和完整 `PixelThemeTokens`。两个公开构造器分别从旧
style 模型建立语义兼容视图，或从完整 token 图一次性投影 legacy style；InheritedWidget 只在不可变
数据变化时通知依赖。标准组件在 mounted build 中读取 `PixelTheme.tokensOf(context)`，因此颜色、
排版、间距、尺寸、圆角、边框、硬阴影、Motion、组件角色和文案都来自同一继承边界。

`PixelColorScheme` 提供 22 个具体语义角色，`PixelComponentTokens` 的 21 个族只保存角色与整数几何。
`resolvePadding`、`resolveMinimumWidth/Height`、`resolveBorderWidth`、`resolveCornerRadius` 和
`resolveElevation` 把标准编码重新映射到当前 foundation scale；不常见的显式整数保持原值。这样复制
一组 foundation token 能改变所有使用该编码的组件，同时仍保持整数像素边界。

`PixelControlStateSet` 是不可变 inline bit set，Normal 使用空 mask。`PixelStateMap` 固定按
Disabled、Loading、Error、Pressed、Focused、Hovered、Selected、Normal 解析单值属性；focus
indicator 单独绘制，所以 Focused 不会覆盖更重要的底色。组件 facade 先归一化回调、enabled、
checked/selected 等业务状态，retained widget 再合入真实 pointer/focus 状态。Loading 保留自动焦点
节点但撤销所有 mutation target，Disabled 同时撤销焦点资格；Host 与 `PixelTester` 在每帧 target
重绑时 cancel 已失效 owner，避免迟到 up 穿透。

`checkThemeTokenCoverage` 从 `PixelComponentTokens` 构造器发现标准族，并要求每一族和十组基础 token
都有生产运行时引用；共享 renderer 通过局部 `when` 选择组件族时，扫描器会沿实际别名使用同时验证
每个可达分支。Token snapshot、真实组件精确 ARGB golden、21×8 生产矩阵、逐组件契约和 Theme
Showcase 分别验证模型、独立颜色通道、行为和可视审阅。完整 API 与迁移边界见
[主题 Token 与组件状态迁移指南](migrations/1.0.0-theme-tokens-and-component-states.md)。

Host 内动画统一使用 `PixelHostView.tickerProvider`。独立构造 provider 仍可用于测试或替代宿主，
但调用方必须自行 pause、resume 和 dispose；它不会自动订阅任意 Host lifecycle。

Host 根树同时注入 `PixelMotionScope`。API 33+ 通过 `ValueAnimator` duration-scale listener，
API 24–32 通过 `Settings.Global.ANIMATOR_DURATION_SCALE` observer 跟随系统设置；detach 注销、
reattach 重读、destroy 终态释放。`PixelHostView.motionSettingsOverride` 只覆盖设置快照，不替换
Host 时钟，设回 null 后继续跟随平台。

`PixelMotionSpec.resolve` 先用饱和运算应用 animator scale，再按 role 处理 reduce motion：feedback、
selection 和 continuous 同步落到可操作终态；spatial 删除 delay，并把非 `None` 运动替换成最长
80ms 的线性 fade。Button、Switch、Slider、Tabs、Slidable、Dialog、Popover、Navigator 和
MultiStack 都从当前 inherited token 解析；运行中 token/设置变化先采样当前视觉值再 retarget，
scale 0/`None` 则同步收敛。Slidable 的直接拖动不插值，release settle 才消费 curve/spring。

交互所有权与 visual 生命周期同步：每份新 render snapshot 会按 RenderObject source identity
重绑 captured click、pressed、slider 和 hover owner。目标卸载、禁用或进入 paint-only 后先发送
一次 cancel/pressed=false，再清除引用；之后的 up 不会调用旧 release，也不会重新命中同坐标背景。
退出中的 Dialog/Popover 和自定义 route presentation 因此可以继续 paint，同时保持唯一 State、
唯一交互 owner 和唯一 semantics 来源。完整策略与迁移示例见
[MotionTheme 迁移指南](migrations/1.0.0-motion-theme.md)。

`PixelAnimationController` 用“segment 起点 + 目标端点 + segment active-time 时长”推进有限动画。
每次 forward/reverse 都先停止旧 ticker，再以当前视觉值或显式 `from` 建立新 segment；完整
`duration` 对应单位距离，中途反向和 stop 后恢复只运行剩余距离，因此不会复用旧 elapsed 或跳回
起点。有限 segment 在任意 overshoot frame 直接写入精确端点并停止 ticker；repeat 则对总 elapsed
做取模/奇偶 leg 计算，不在边界反复 stop/start，所以单帧跨越多个周期仍确定且不会丢失余量。

controller 的 `isAnimating` 读取 ticker 活跃态，而不是从 `Forward/Reverse` status 推断：stop 后可
保留方向供观察，同时明确报告不再调度。零时长命令同步收敛，负时长在 ticker 创建前失败；Host
pause/resume 依赖 provider 的 pause-excluding active clock，恢复首帧只重建 raw-time 锚点。以上路径
由 `ManualFrameScheduler` 直接注入绝对纳秒时间测试，不依赖 sleep 或 Android Looper。

`AnimatedOpacity` 始终保留同一个 `RenderOpacity`：只在 alpha 为零时跳过 paint、hit test、
所有交互 target 和 semantics，layout 与 retained State 仍然存活。`AnimatedSwitcher` 则维护一组
带独立 wrapper key 的 visual entry，共享一条 segment 时钟计算各自 opacity；中断时先快照
当前视觉 alpha，再从该快照开始新 segment，避免子树跳变或提前卸载。该设计的
对外行为见 [动画正确性迁移指南](migrations/1.0.0-animation-correctness.md)。

### 图像、图形和资源

图像与资源：

- `PixelBitmap`
- `PixelBitmapAssetLoader`
- `PixelBitmapResourceLoader`
- `PixelSpriteSheet`
- `PixelSpriteSheetJsonLoader`
- `PixelResourceManifestJsonLoader`
- `PixelResourceCache`
- `PixelResourceLoader`

sprite sheet schema 分两层稳定：

- v1 简单 sheet 只描述 `bitmap` 和矩形 `frames`，用于 `Sprite` / `AnimatedSprite` 的直接帧绘制。
- v2 atlas 增加 `scale`、裁剪前尺寸、trim 和 pivot；`loadAtlas` 会保留这些 metadata，`load` 仍只产出传统 `PixelSpriteSheet`。
- loader 不加载 bitmap，也不解释 resource manifest 的 id；资源定位由调用方或资源目录层完成。
- manifest/sprite/glyph parser 共享严格有界 JSON 与二进制校验内核，先限制输入、深度、数量、尺寸和精确长度，再分配集合或像素；可选 SHA-256 在解码前验证。

resource cache 提供有界并发复用：

- bitmap、sprite sheet 和 glyph pack 有逐类字节/条目预算，同时共享总字节预算与全局访问序。
- 同类同 key 并发未命中只执行一次锁外 loader；`remove` / `clear` 使旧在途任务失去写回资格。
- `snapshot()` 保留旧计数契约；`detailedSnapshot()` 和锁外 eviction listener 提供字节、LRU、拒绝与在途可观测性，且不持有资源引用。
- `PixelBitmap` 与 `PackedGlyphRecord` 在公开构造和读取边界 defensive copy；引擎只在模块内只读热路径使用 owned storage，避免每帧复制。

正式加载层不拥有线程：

- `PixelResourceLoader` 接收宿主 executor 和共享 cache；同步入口默认拒绝 Android 主线程，异步入口负责同 key 去重、独立订阅取消、预取和短期失败缓存。
- 取消只结束当前 subscriber，不取消共享 IO；这避免一个页面离开时破坏其他页面正在等待的同一资源。
- bitmap 先校验编码长度/magic/checksum 和 bounds，再正式解码；glyph 校验完整头、count/scalar/长度/重复/尾随；JSON 拒绝重复 key、尾随垃圾和非整数协议值。
- 资源包切换、低内存或页面销毁时仍由调用方主动 `remove` / `clear`，自动 LRU 是上限而不是生命周期替代品。

资源打包工具当前只覆盖 glyph pack：

- `tools/generate_pixel_glyph_packs.py` 将 TTF / OTF / BDF 转成 `manifest.json + glyphs.bin`。
- `:pixel-engine:generatePixelGlyphPacks` 只重建 app 内置 Fusion Pixel 字形包。
- sprite sheet 和 resource manifest/catalog 暂按稳定 JSON schema 手写，不引入额外打包工具。

图形组件：

- `Image`
- `Sprite`
- `AnimatedSprite`
- `Line`
- `Circle`
- `Polygon`
- `Path`
- `CustomPaint`

## 8. 性能策略

关键策略：

- `PixelBufferPool` 按尺寸复用 buffer
- `PixelBufferPool` 用单元测试覆盖同尺寸复用、复用前清零、桶上限和禁用缓存场景
- `PipelineOwner` 维护 layout / paint 脏标记
- `updateRenderObject` 先做字段 equality 检查，再决定 `markNeedsLayout` / `markNeedsPaint`
- `PixelBuffer.blit` 在可用时按行 `arraycopy`
- `PixelFontEngine` 使用 LRU glyph 缓存
- 文本换行保持线性扫描
- `EnginePerformanceSmokeTest` 固定输出 list scroll、text input、animation、page transition、overlay 场景报告；报告用于趋势对比，不作为跨机器硬阈值。
- `PixelHostFrameDiagnostics` 把 build、layout、logical paint、buffer submit、exclusive Android
  draw 和 total 关联到 dirty node、logical pixel、ART allocation/GC、buffer pool 与 render
  cache；deadline reason 取最大互斥阶段，纯交付延迟归为 `FRAME_SCHEDULER`，未归因且观察到
  GC 时归为 `GARBAGE_COLLECTION`。
- 完整诊断默认关闭；disabled path 只经过 primitive boolean branch，不采样 ART、不遍历 dirty
  subtree、不读取 buffer pool stats，也不创建 frame snapshot。Inspector/observer 显式启用后每帧
  读取两个 ART boundary sample，并创建有界的小型快照对象。
- 当前继续整帧提交；只有 baseline 或真实设备 smoke 证明整帧提交成为瓶颈时，才设计 dirty region / partial repaint。

开发要求：

- paint 热路径不要分配大对象
- 自定义 render object 改配置时先判断字段是否真正变化
- 尺寸变化用 `markNeedsLayout`
- 仅颜色或内容变化用 `markNeedsPaint`
- 所有 runtime 变更在主线程执行

### 0.x API 兼容策略

`pixel-engine` 的 `1.0.0` 候选已经进入 SemVer 稳定边界。公开 API 变更必须先审阅各 artifact 的
Metalava/JVM ABI diff；有意的破坏性变更必须遵循弃用周期、更新 baseline，并同步根目录
`CHANGELOG.md` 与 migration guide。
完整 SemVer、弃用周期和 migration guide 规则见 `pixel-engine/docs/发布与兼容策略.md`。

1.x baseline 规则：

- 新增 public API：确认 KDoc、手册和示例同步更新，再更新 `pixel-engine/api/pixel-engine.api` 与 `pixel-engine/api/pixel-engine.binary-api`。
- 修改任一拆分 artifact 的稳定面：还必须审阅并更新该模块 `api/*.metalava-api` 与 `api/*.binary-api`；带内部标记的 sibling bridge 不属于稳定 API。
- 删除、重命名或签名变化：必须在 `CHANGELOG.md` 的当前版本下记录 breaking change，并在同一提交更新 public / binary baseline。
- 仅实现、测试或文档变化：不应修改 baseline；如果 `checkPublicApi` 或 `checkBinaryApi` 失败，先确认是否误暴露了 API。
- baseline 更新命令：

```bash
./gradlew :pixel-engine:dumpPublicApi :pixel-engine:dumpBinaryApi --no-daemon
cp pixel-engine/build/reports/api/pixel-engine.api pixel-engine/api/pixel-engine.api
cp pixel-engine/build/reports/api/pixel-engine.binary-api pixel-engine/api/pixel-engine.binary-api
```

提交前必须跑默认无设备发布门禁：

```bash
./tools/pixel-release-check.sh
```

## 10. 开发规则

- 新底层像素能力放入 `pixelcore`
- 新 widget、layout、输入、滚动、导航能力放入 `pixelui`
- 业务产品语义留在调用方 app，不进入 engine
- 新 SDK 能力必须补单测
- 可视化能力必须在 `pixel-demo` 增加验收场景
- 不恢复旧 bridge lowering 或 legacy render backend
- 新增或迁移 artifact 必须先更新受审 ownership/dependency manifest，并通过无环、平台 import、重复 class、独立消费者和聚合 API/ABI 门禁
- 公开 API 需要保持 explicit visibility 和清晰 KDoc
