# Pixel Engine 架构与设计

## 1. 工程边界

主工程当前包含以下四个 Gradle 模块：

<!-- architecture-contract:modules:start -->
- `:app`
- `:pixel-engine`
- `:showcase`
- `:showcase-desktop`
<!-- architecture-contract:modules:end -->

`:app` 和 `:showcase` 通过 Gradle project 依赖消费 `:pixel-engine`。`:showcase-desktop` 是特殊的
JVM/AWT 验证宿主：它编译前触发 `:pixel-engine:exportDebugClassesJar`，消费从 debug AAR 解包到
稳定自有路径的 `pixel-engine/build/outputs/desktop-classes/classes.jar`，并共享 `:showcase`
的场景源码；它不构成新的 Engine Library。`pixel-engine` 仍是唯一 Android Library 和唯一 Maven
坐标；源码职责通过 package、接口、Kotlin 可见性和测试表达，不通过额外 Gradle project 表达。

```text
pixel-engine
├── com.purride.pixelcore                  像素、字体、bitmap、sprite、资源
├── com.purride.pixelui                    Widget、Element、RenderObject、组件、路由与恢复
├── com.purride.pixelui.host               Android Host 与平台桥
├── com.purride.pixelui.testing            确定性测试 DSL
└── com.purride.pixelui.debug              检查器与诊断
```

`app` 和 Android `showcase` 只能依赖公开 API；Engine 不得反向依赖 Launcher 或展示宿主类型。产品
文案、图标和业务状态留在 `app`。

## 2. Retained tree

引擎 UI 生命周期分为三层：

1. Widget 描述不可变配置和子树。
2. Element 管理挂载、更新、Inherited 依赖、State 和 owner。
3. RenderObject 执行约束布局、绘制、命中测试和 semantics。

更新时优先复用 Element 与 RenderObject，只把真实变化传播到 layout 或 paint 阶段。State、焦点、滚动
和路由身份依赖稳定 type/key/entry，不依赖当前 index 或可变 label。

## 3. 帧、动画和生命周期

生产 Host 使用 `ChoreographerFrameScheduler`，测试使用 `ManualFrameScheduler`。动画、ticker 和回调
必须可取消；detach 只暂停，owner destroy 或 `dispose()` 才执行终态释放。Activity 在 `onDestroy`、
Fragment 在 `onDestroyView` 释放 `PixelHostSetup`。

## 4. Android Host

`createPixelHostSetup` 创建 `PixelHostView`、文本输入桥和根容器，并连接 Lifecycle、触摸、键盘、焦点、
IME、WindowInsets、density、configuration、Accessibility 和 Back dispatcher。

当前不发布 Compose wrapper。Compose 应用可以在应用层用 `AndroidView` 承载 `setup.rootView`，并遵循
同样的 owner 与 dispose 规则，避免 Compose compiler 改写 Engine 公开 ABI。

## 5. 主题、组件和输入

主题由语义 token、motion token 和组件状态集合组成。标准组件允许显式覆盖，但不得硬编码 Launcher
业务。组件至少覆盖 normal、disabled、focused、pressed 及自身必要状态，并提供布局、交互、像素输出
和语义测试。

文本公开 offset 与 Android 保持 UTF-16 语义；编辑、selection、caret 和 hit test 必须对齐 Unicode
grapheme。键盘、DPAD、触摸、IME 和 Accessibility 共享稳定语义身份。

## 6. 路由与恢复

导航使用 typed destination、request、entry 和 outcome。Snapshot adapter 带版本，恢复必须先完整验证
再提交，失败时保留旧状态。Back 按 Overlay、焦点、子导航、宿主的顺序消费。

## 7. API 分层

### 稳定层

`com.purride.pixelcore`、`com.purride.pixelengine` 和 `com.purride.pixelui` 的公开契约受 Kotlin API、
Metalava 与 JVM binary baseline 保护。稳定类型不能无弃用周期删除、改名或改变 JVM 描述符。

### 高级 SPI

`com.purride.pixelui.advanced` 提供真实 RenderObject 扩展点。消费者实现自定义渲染时：

1. Widget 的 `createRenderObject` 只创建一次 RenderObject。
2. `updateRenderObject` 精确比较字段；尺寸变化标记 layout，视觉变化标记 paint。
3. layout 通过 `PixelRenderConstraints` 约束 `PixelRenderSize`。
4. paint 使用 `PixelPaintContext` 和传入的 offset/clip，热路径避免持久分配。
5. 可交互对象同时实现 hit test、焦点、键盘和 semantics。
6. dispose 释放 listener、ticker 与 child owner。

高级 SPI 仍是公开契约，但复杂度和兼容风险由使用者承担。第三方不得 import `internal.*`。

### 实验层

`@PixelExperimentalApi` 要求显式 opt-in。实验 API 仍需中文 KDoc、行为测试、Changelog 和迁移说明，
但允许在 minor 版本中按发布策略演进。

### 内部层

`internal` package 和带内部二进制标记的声明不属于消费者稳定 API。部分 JVM public 描述符仅为既有
内部兼容保留，不代表第三方可调用。

## 8. 质量边界

- JVM 测试覆盖布局、绘制、状态、路由和测试 DSL。
- instrumentation 覆盖真实 Android Host。
- API/ABI baseline 阻止无意破坏。
- 隔离 Maven consumer 覆盖 Java/Kotlin、R8 和自定义 SPI。
- AAR 预算限制 bytes、class、method 与依赖图。
- 发布工具检查 POM、metadata、lockfile、SBOM、checksum 和签名。

性能 benchmark 与设备 soak 已移出当前工程；未来需要先定义设备、场景、采样方法和噪声处理，再建立
独立性能目标。
