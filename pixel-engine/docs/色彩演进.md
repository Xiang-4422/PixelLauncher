# pixel-engine 色彩演进

> 本文档不是已有功能说明，而是 **未来色彩系统的设计方向**。
> 目的：在动手实现前，把"彩色模式 / 单色模式如何并存、API 怎么暴露"写清楚，避免提早做出无法回退的渲染层决定。

最后更新：2026-05-20

---

## 1. 背景

当前 `pixel-engine` 是**严格三色调色板**：

- `PixelTone.OFF / ON / ACCENT`，对应 `PixelBuffer` 中的字节值 `0 / 1 / 2`。
- `PixelBuffer` 底层是 `ByteArray`（每像素 1 字节），blit / clear / setPixel 全部按字节操作。
- 颜色映射到屏幕由 `PixelPalette`（5 个预设主题）在最终 paint 时一次性完成。

这是当前最大化"像素风一致性"的设计。但要走向通用 SDK，需要承认两类需求：

1. **彩色场景**：游戏 HUD / 工具应用 / 仪表盘等可能需要任意 RGB 颜色和真 alpha。
2. **单色场景**：复古风、e-ink、Game Boy 仿真等仍要保留当前严格三色路径。

未来方向：**SDK 支持彩色模式 + 单色模式两套并存**。用户用一个全局开关切换；单色模式内沿用现有主题系统。

---

## 2. 模式定义

### 2.1 Mono Mode（单色模式）

完全等价于当前实现：

- 像素只能是 `PixelTone.OFF / ON / ACCENT`。
- 屏幕呈现由 `PixelPalette` 一次性决定（GREEN_PHOSPHOR / AMBER_CRT / ICE_LCD / MONO_LCD / NIGHT_MONO）。
- 透明度是离散档位（`PixelTone.toAlpha()` 体系）。
- 主题切换 = 切 `PixelPalette` + 切 tokens。
- **这是 SDK 的默认模式**——保证现有所有 demo / 业务代码零迁移。

### 2.2 Color Mode（彩色模式）

像素仍然是整数网格、整数坐标，但每个像素可取任意 ARGB：

- 颜色类型由 `PixelColor`（新抽象）承载，内部存 ARGB Int。
- 真 alpha 混合（与 Android Canvas 一致）。
- 主题系统仍然存在，但 tokens 直接给出 `PixelColor`，不经 `PixelPalette` 映射。
- `PixelTone` 在彩色模式下仍可使用——隐式 widget / 现有 demo 代码不必改写——但其值通过当前主题的"等价色"映射成 `PixelColor` 再落 buffer。

### 2.3 切换语义

- 全局开关：`PixelHostSetupConfig.colorMode: PixelColorMode = Mono`（默认）。
- **不允许混合**：一个 `PixelHostView` 实例在生命周期内只能是单一模式；不支持 widget 树某子树彩色、另一子树单色。理由：buffer 存储格式不能逐子树切换。
- 多 HostView 可以分别配置不同模式（理论上）。

---

## 3. 现有概念在两种模式下的语义

| 概念 | Mono Mode | Color Mode |
|---|---|---|
| `PixelTone` | 直接落 byte 0/1/2 | 通过 tokens 映射成 `PixelColor` 后落 ARGB |
| `PixelPalette` | 决定屏幕呈现 | **不再使用**，颜色直接走 PixelColor |
| `PixelTheme` 5 个预设 | 切 palette + tokens | 仅切 tokens（颜色已是 PixelColor） |
| `PixelTextStyle.tone` | 仍然有效 | 仍然有效（通过 tokens 映射） |
| `PixelTextStyle.color`（新增） | 忽略 / 警告 | 优先于 tone |
| 透明度 | 离散档位（0% / 50% / 100%） | 真 alpha 0..255 |
| `PixelBuffer` 底层 | `ByteArray`，每像素 1 字节 | `IntArray`，每像素 4 字节 |
| blit | 字节 arraycopy | int arraycopy + 可选 alpha blend |

## 4. 核心 API 影响

### 4.1 `PixelColor` 抽象（新增）

```
class PixelColor(val argb: Int)  // 仅示意，签名实现时再定
```

需要决策：

- 是 inline value class 还是 data class？（性能 vs 调试便利）
- 如何与 `PixelTone` 互转？（提供 `PixelTone.toPixelColor(theme: PixelThemeData): PixelColor`？还是必须显式经 tokens？）
- 是否预定义常量集合 `PixelColors.Red / Green / Blue / ...`？（彩色模式下用户期望有便利常量）

### 4.2 `PixelPaintContext` 扩展

当前 paint 接口是 `buffer.setPixel(x, y, toneValue: Int)`，未来需要兼容：

- Mono 模式 setPixel 仍然吃 `Int (0/1/2)`。
- Color 模式 setPixel 吃 `Int (ARGB)`。
- 同名同签名可能引发误用——更安全的方案是分别提供 `setTone(x, y, tone)` 和 `setColor(x, y, color)`，由 mode 决定哪个生效。

### 4.3 公开 widget 参数

新增彩色相关参数走**追加而非替换**：

- `Container(tone, color = null, ...)`：tone 是兼容入口，color 是彩色入口；color 非空时优先。
- `PixelTextStyle(tone, color = null, ...)`：同上。
- Mono 模式下传 color 报警告 / fallback 到 tone。

### 4.4 主题 / Tokens 重构

`PixelThemeTokens` 需要承载两种类型的"颜色源"：

- 选项 A：**统一抽象**——所有颜色字段都是 `PixelColor`，Mono 模式下通过 palette 反向把 PixelColor 量化回 PixelTone。
- 选项 B：**并存字段**——`textTone: PixelTone` 与 `textColor: PixelColor?` 并存，模式决定读哪个。

**倾向**：B 选项更直观，但 token 数量翻倍。需要在落地前定。

## 5. 渲染层影响

### 5.1 `PixelBuffer` 存储扩展

当前是 `ByteArray`。彩色需要 4 字节 / 像素。两种实现路径：

- **双类型 buffer**：`MonoPixelBuffer (ByteArray)` 和 `ColorPixelBuffer (IntArray)` 分开，渲染管线按 mode 选择。
- **统一 buffer**：`PixelBuffer` 内部持有 union，根据 mode 切换访问路径——但每次 setPixel 多一次 mode 检查，热路径开销。

**倾向**：双类型，避免热路径分支。代价是 RenderObject 写自定义 paint 需要意识到 mode。

### 5.2 `PixelBufferPool` 适配

当前池按 `(width, height)` 索引。未来需按 `(width, height, mode)` 索引；mono / color buffer 互不通用。

### 5.3 字体栅格化

`PixelFontEngine` 当前输出 1-bit 字形掩码（"这个像素是 ON 还是 OFF"）。

- 彩色模式下，字形仍然是 1-bit 掩码——字体设计本身是像素的；颜色由 paint 时 setColor 决定。
- 不需要为彩色模式重写字体子系统。

### 5.4 blit / arraycopy

- Mono：`System.arraycopy(byteArray, ...)`。
- Color：`System.arraycopy(intArray, ...)`，单像素 4 字节带宽翻倍。
- alpha blend：仅彩色模式需要；mono 模式下"透明度"是离散档位不走 blend。

**性能预期**：彩色模式 blit 带宽 4x，但实际帧渲染瓶颈未必在 blit；需要彩色模式专属的 `PerfBaselineTest` 项。

## 6. 兼容性策略

强约束：**默认 Mono Mode，所有现有 demo / 业务代码零迁移**。

- `PixelHostSetupConfig.colorMode` 默认 `Mono`。
- 现有所有 widget 签名不变；新参数（`color`、`PixelColor`）全部带默认值。
- `pixel-demo` 现有 21 个场景继续运行在 Mono 模式。
- 新增彩色 demo 场景显式 `colorMode = Color` 入口。

向后兼容窗口：在彩色模式落地后**至少保留 2 个版本**让用户迁移；不强制彻底切换。

## 7. 不做的部分

| 取舍 | 决策 |
|---|---|
| 子树级 mode 切换（一棵树内部分彩色 + 部分单色） | ❌ 不做。Buffer 存储格式不能逐 node 切换。 |
| HDR / 10-bit / sRGB / Display-P3 色彩管理 | ❌ 不做。SDK 定位是像素艺术，不是色彩准确性。 |
| 渐变填充（linear / radial gradient） | ⏸ 暂不做。等彩色模式落地后再看需求。 |
| 像素位深可配置（4-bit / 8-bit 调色板模式） | ❌ 不做。两套模式已经够覆盖需求；多模式会膨胀渲染层。 |
| Mono → Color 自动迁移工具 | ❌ 不做。两种模式视觉差异大，需要用户主动设计。 |

## 8. 落地分层

按依赖顺序，每一层可独立 commit、独立验证。

### Phase A — 渲染层基础设施（最重，先做）

- 新增 `PixelColor` 类型 + 常量集合。
- `PixelBuffer` 拆为 `MonoPixelBuffer` / `ColorPixelBuffer`，或扩展统一接口。
- `PixelBufferPool` 按 `(w, h, mode)` 索引。
- blit / clear / setPixel 在两种 buffer 上各自实现。
- `PerfBaselineTest` 增加彩色路径指标。
- **不动公开 widget API**——这一层纯内部。

### Phase B — 主题与 token 重构

- `PixelThemeTokens` 增加 `PixelColor` 字段（选项 B）或统一抽象（选项 A）。
- `PixelThemeData.resolveXxxStyle()` 增加 `colorMode` 参数。
- `PixelTheme` 5 预设各自定义彩色模式下的 tokens。

### Phase C — 公开 widget API 扩展

- `Container` / `Text` / `RichText` / `PixelTextStyle` 等增加 `color: PixelColor?` 参数。
- `PixelPaintContext.setColor()` 公开。
- `pixelui.advanced` 门面下 RenderObject 基类增加彩色入口。
- 文档更新：组件目录 / 主题系统。

### Phase D — Mode 切换 + Host 集成

- `PixelColorMode` 枚举（Mono / Color）。
- `PixelHostSetupConfig.colorMode` 字段。
- `PixelHostView` 根据 mode 配置 buffer pool 与渲染管线。
- demo 新增 `COLOR_MODE_SHOWCASE` 场景对比两种模式。

### Phase E — 文档 / 验收

- 文档全面更新：架构说明 / 主题系统 / 组件目录 / 扩展开发。
- 彩色模式专属的 golden / element snapshot 测试。
- 在 `演进路线.md` 中把 Phase A-E 拆解为可执行任务。

## 9. 开放问题

落地前需要先决定的：

### Q1：`PixelColor` 与 `PixelTone` 互转语义？

- 选项 A：`tone.toPixelColor(theme)` 走 tokens 映射——隐式依赖 theme。
- 选项 B：必须显式 `tokens.colorFor(tone)`——啰嗦但显式。

**倾向**：B。隐式映射会导致同样的 widget 在不同 theme 下视觉漂移，且难以追踪源头。

### Q2：tokens 是统一抽象（A）还是并存字段（B）？

参见 §4.4。**倾向 B**，但需要明确 token 命名规则（例如 `textTone` / `textColor` 共存）。

### Q3：Mono 模式下用户传 `color` 参数如何处理？

- 选项 A：silently fallback 到 tone。
- 选项 B：开发时 warning 日志。
- 选项 C：debug 构建抛异常，release 构建 fallback。

**倾向**：C。让开发期立即暴露错误模式使用。

### Q4：`PixelBuffer` 是拆双类型还是统一接口？

参见 §5.1。性能 vs 易用性的取舍。**倾向**：双类型。RenderObject 作者本来就需要意识到 mode。

### Q5：彩色模式是否需要 "compatibility palette"？

即：彩色模式下提供一个虚拟 `PixelPalette`，让用户即使在彩色模式也能用现有"5 预设主题"的色调感觉。

**倾向**：不专门做。彩色模式的用户期待是"自由配色"，强行套预设反而别扭。但 demo 可以提供"彩色版 GREEN_PHOSPHOR"等示例供参考。

### Q6：是否允许动态切换 mode？

即：运行时 `hostView.colorMode = Color`，触发渲染管线重建。

- 优点：调试 / 主题切换体验好。
- 缺点：buffer pool / RenderObject 缓存全部失效，可能引入边界 bug。

**倾向**：先不做。Mode 应在 HostSetupConfig 一次性确定。

### Q7：彩色模式下"主题切换"还有意义吗？

彩色模式下用户可以自由配色，"主题"概念退化为"一组预定义 tokens 集合"。

- 选项 A：保留 5 预设主题，仅作为示例 tokens。
- 选项 B：彩色模式不内置任何预设主题，用户自己定义。

**倾向**：A。即使是自由配色场景，提供"可参考的色彩搭配"对入门用户也有价值。

## 10. 引用与不在范围内

- 单色模式下的主题已在 [主题系统](主题系统.md) 详述，本文档不复述。
- 像素艺术的色彩设计原则（如 PICO-8 16 色 / Game Boy 4 灰阶 / EGA 调色板）可作为彩色模式 demo 的灵感来源。
- 本文档**不**定义：
  - 具体类签名（实现时再设计）
  - 性能基准数字（实现 Phase A 后再用 `PerfBaselineTest` 补）
  - 调色板预设的具体颜色值（彩色模式实现时再确定）

本文档只回答："彩色模式应该怎么和单色模式并存、API 怎么不破坏现有用户。"
