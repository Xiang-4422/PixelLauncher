## 1. 文档职责

本文是把 `pixel-engine` 从内部 `0.x` 引擎推进到具备对外发布质量、可长期维护的 Android 像素 UI SDK 候选的执行规格。未来使用 Goal 模式时，应以本文的未完成工作、依赖关系和验收条件为准，而不是根据已有类名、已有测试数量或旧规划中的勾选状态判断任务已经完成。真实外部发布由后续独立 Goal 执行。

相关文档的职责如下：

- `pixel-engine/docs/长期规划.md` 负责描述产品愿景和长期边界。
- `pixel-engine/docs/发布与兼容策略.md` 负责定义 SemVer、弃用和迁移规则。
- `pixel-engine/docs/架构与技术实现.md` 负责描述已经落地的架构，而不是未来计划。
- `pixel-engine/docs/使用说明与API手册.md` 负责面向 SDK 使用者说明稳定行为。
- 本文只负责记录走向 `1.0.0` 的未完成工作、执行顺序、验收证据和完成定义。

如果其他规划文档中的 `[x]` 与本文的现状证据或验收条件冲突，应重新验证，不得直接继承“已完成”状态。

## 2. 总目标

把当前功能覆盖较广但契约仍处于内部 Alpha 阶段的 `pixel-engine`，建设为具备下列能力的稳定 Android SDK：

- 公共 API、二进制 API 和行为兼容边界明确且可自动检查。
- 路由、状态恢复、生命周期、动画和输入行为具有可测试的稳定契约。
- 自绘 UI 对 TalkBack、键盘、手柄和 Switch Access 等输入方式可用。
- UI 组件共享完整的主题、状态、国际化和自适应体系。
- 资源解析、缓存和内存所有权具有明确边界，不因恶意输入或生命周期错误破坏宿主。
- 扩展点不依赖内部实现，宿主服务可以注入、替换和独立测试。
- 运行时、测试、调试和可选适配层按职责发布，不污染最小消费者产物。
- 发布产物具备正确元数据、签名、文档、兼容矩阵和迁移策略。
- 仓库与发布产物中不存在密钥、明文敏感信息或不受控备份。

## 3. 当前基线

以下数据是 2026-07-12 审计快照。Goal 启动时必须重新采集，并把差异写入执行记录。

### 3.1 已验证能力

- 已有 `:pixel-engine`、`:pixel-demo` 和 `:app` 三个模块。
- 引擎已有 retained Widget/Element/RenderObject、布局、文本、列表、网格、sliver、输入、焦点、路由、动画、测试和诊断基础能力。
- 699 个引擎 JVM 测试和 9 个 Demo JVM 测试通过，无失败或跳过。
- Lint、Release AAR、Demo 构建、公共 API baseline、二进制 API baseline 和独立消费者 smoke 通过。
- Release AAR 约 1.4 MiB，包含约 730 个 class entry。
- 当前 `minSdk=24`、`compileSdk=36`、版本为 `0.1.0-SNAPSHOT`。

### 3.2 已知发布阻断

- `app` 中提交了硬编码的第三方 AI API Key，并使用普通 `SharedPreferences` 保存设置；备份排除规则尚不完整。
- `pixelui.advanced` 使用 typealias 暴露 `pixelui.internal` 实现，而当前 API 检查会过滤这些 internal 目标，存在兼容性漏检。
- Navigator 的恢复数据主要是 route 名称，缺少独立 entry ID、参数、结果通道和版本化状态；同一 route 实例重复入栈可能共享恢复状态。
- `AnimatedSwitcher`、`AnimatedOpacity` 和 `PixelAnimationController` 存在中间帧、透明度应用或状态切换正确性问题。
- Semantics 信息有限，Android 虚拟无障碍节点缺少稳定身份、完整层级和动作集合。
- 当前性能 smoke 是 JVM 时间采样，没有覆盖真实 `Canvas` submit，也没有可阻止回归的阈值。
- 没有 `pixel-engine/src/androidTest` 设备测试，也没有 Macrobenchmark、Microbenchmark 或 Baseline Profile。
- 单一 AAR 同时包含 runtime、widgets、navigation、testing 和 debug/inspector 类。
- 资源缓存缺少字节上限和 LRU；部分资源解析器缺少严格的尺寸、版本和完整性校验。
- 公共 KDoc 报告为 `451 / 996`，覆盖率 `45.28%`，当前门禁只有 `35%`，且扫描方式会漏掉部分声明。
- SDK 文档没有进入当前 MkDocs 站点，长期规划、发布清单和实际代码存在状态漂移。

## 4. 硬约束

下面的约束适用于所有里程碑，不得通过缩小测试范围、降低阈值或改变定义绕过。

### 4.1 代码与注释

- 所有新增或修改的类、变量（包括属性、成员变量和局部变量）和方法都必须有必要的注释说明。
- 所有 public/protected API 必须有 KDoc，说明职责、参数、返回值、异常、生命周期、线程约束和兼容性语义中适用的部分。
- 内部状态变量、缓存、调度器、所有权转移和非直观局部变量必须说明用途及不变量。
- 注释应解释“为什么、何时以及有什么约束”，不能只重复标识符名称或代码表面行为。
- 完成 Goal 前应同步修订根 `README.md` 中与本约束冲突的旧注释约定。

### 4.2 兼容性与质量

- 不允许稳定公共 API 指向 `internal` 包或依赖内部实现类型。
- 不允许为通过检查而删除测试、扩大 baseline 忽略范围或降低覆盖率/性能阈值。
- 任何 breaking change 必须同时更新 API baseline、CHANGELOG 和 migration guide。
- 对外公开的新能力必须同时提供测试、KDoc、使用手册和 Demo 或最小示例。
- 所有 Android UI/runtime 操作必须有明确的主线程契约；后台工作必须明确调度和取消规则。
- 错误边界不得吞掉虚拟机错误、线程终止等不可恢复的 fatal error。

### 4.3 安全与外部操作

- 禁止在源码、资源、BuildConfig、测试夹具、日志或发布产物中提交真实密钥。
- Git 历史重写、密钥吊销、远程仓库强制推送、许可证选择和真实 Maven 发布需要显式用户授权或凭据。
- 当前范围内需要授权的历史清理与许可证选择已经完成；真实 Maven 发布不属于当前 Goal。

### 4.4 产品边界

- 保持 Android-first，不把本 Goal 扩张为跨平台引擎。
- 不复刻 Flutter 全 API，不建设 Material/Cupertino 替代库。
- 不为了组件数量添加没有真实像素 UI 场景的组件。
- 不把 PixelLauncher 主界面改写为 Compose；Compose 只允许作为可选 SDK 适配层。

### 4.5 当前 Goal 的性能边界

- 不继续运行 Macrobenchmark、Microbenchmark、性能 trace、性能趋势复跑或性能 soak。
- 不继续调整帧时间、p95/p99、jank、allocation 或设备频率问题，也不为这些指标修改生产代码。
- 已经完成并通过的性能基础设施、Baseline Profile、优化代码和验收归档保持原状，不回退、不删除。
- M6-2 剩余代表设备矩阵、120Hz、批准基线复跑和阈值验收移交给后续独立性能 Goal。
- 当前 `1.0.0` 仍必须通过功能正确性、安全、API/ABI、无障碍、资源边界、消费者和发布验证。

### 4.6 当前 Goal 的正式发布边界

- 当前 Goal 必须产出版本/API 冻结、完整非性能门禁、功能设备 smoke、隔离 Maven publication、签名
  staging、SBOM/provenance/checksum、消费者矩阵、文档和独立制品复核均通过的 `1.0.0` 候选。
- 不在当前 Goal 创建或推送正式 tag，不写入最终发布日期，不发布 GitHub Release 或部署公开文档站。
- 不在当前 Goal 选择/验证 Maven Central namespace，不配置长期 OpenPGP 私钥，也不执行真实仓库上传。
- main branch protection、Pages 启用、GitHub Support 旧对象缓存清除和发布后全新消费者验证移交未来
  独立发布 Goal；已有只读检查器和防误发布预检保留为后续硬门禁。

## 5. 执行与状态协议

### 5.1 状态定义

工作包状态只允许使用：

- `未开始`：尚未开始实现。
- `进行中`：已经产生实现或验证工作，但验收条件尚未全部满足。
- `阻塞`：剩余工作依赖用户授权、外部凭据或当前无法控制的外部状态。
- `非当前范围`：用户明确移出当前 Goal；已有成果保留，未完成项不计入当前依赖与 Definition of Done。
- `已完成`：实现、测试、文档和验收证据全部满足。

所有工作包初始状态均为 `未开始`。已有同名 API 或旧文档中的 `[x]` 不能作为完成证据。

### 5.2 完成证据

每个工作包完成时必须在本文末尾的执行记录中写明：

- 完成日期和相关提交或工作区变更摘要。
- 新增或修改的核心文件。
- 执行过的测试命令及结果。
- API baseline、截图、AAR 或发布元数据等当前范围产物路径。
- 仍保留但不阻止该工作包完成的风险；P0/P1 风险不得遗留到 `1.0.0`。

### 5.3 依赖顺序

默认顺序为：

```text
M0 → M1 → M2/M3 → M4 → M5/M6/M7 → M8 → M9
```

- M2 和 M3 可以在 M1 稳定核心 API 后并行。
- M5、M6、M7 可以在 M4 的语义、焦点和 Overlay 契约确定后并行。
- M6-2 已移交后续性能 Goal，不再阻塞 M8、M9 或当前 `1.0.0` Definition of Done。
- M8 的测试基础设施应随各阶段同步建设，但其最终兼容矩阵必须在模块边界稳定后收口。
- M9 只有在所有 P0/P1 工作包完成后才能进入候选发布。

### 5.4 并行执行、批量门禁与进度证据

- 同一时间最多保留一个 root 集成任务和三个独立子任务。子任务必须有不重叠的可写范围和明确证据目标；共享文件、baseline 和最终集成冲突由 root 统一处理。
- 子任务先运行最接近改动的定向测试，并回传命令、结果、覆盖范围和遗留风险；不得为每个子任务重复执行完整 JVM、golden、API 或发布回归。
- root 在一批互不重叠的改动集成后，对该批只执行一次受影响的聚合门禁；到达子包/工作包收口点或修改全局契约时，再执行完整 JVM、snapshot/golden、API、文档和发布门禁。任一失败都必须回到定向复现与该批聚合复验，不得降低门禁。
- 进度以本文的可见子包、勾选项和执行记录为准；测试数量、并行任务数量或局部通过不能代替实现、测试、文档和验收证据。未完成项不得提前勾选，上层工作包必须在全部子包和总验收通过后才能改为`已完成`。

## 9. Goal 模式续作协议

每次 Goal 续作应遵循以下顺序：

1. 读取本文、最近执行记录、`git status` 和相关代码，不从头重做已提供证据的工作。
2. 重新确认当前最早的未完成且未阻塞工作包。
3. 先运行与该工作包最接近的失败测试或建立能够复现缺口的测试。
4. 完成最小闭环实现，同时补齐必要注释、KDoc、测试、Demo 和文档。
5. 运行局部门禁，再运行受影响的聚合门禁。
6. 记录证据后才更新工作包状态；失败或只完成部分内容时保持 `进行中`。
7. 遇到可以安全推导的实现细节应继续推进；只有许可证、凭据、破坏性 Git 操作、真实发布或会改变产品边界的选择才请求用户决策。
8. 只在全局 Definition of Done 全部满足且没有必需工作时，把 Goal 标记为完成。
