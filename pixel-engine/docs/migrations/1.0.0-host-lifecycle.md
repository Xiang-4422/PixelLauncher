# pixel-engine 1.0.0 Host 生命周期与调度迁移指南

## 范围

M2-3 把 `PixelHostView` 的 Window attachment、owner lifecycle 和终态释放拆成独立语义，并让
每个 Host 独占自己的 frame/ticker scope：

- `onAttachedToWindow` / `onDetachedFromWindow` 只描述 View 是否属于 Window；
- `start`、`resume`、`pause`、`stop` 描述可恢复的运行状态；
- `destroy` / 旧 `dispose()` 描述不可恢复的终态；
- attach 时自动发现 `ViewTreeLifecycleOwner`，也允许显式绑定 `LifecycleOwner`；
- `PixelHostView.tickerProvider` 由 Host 私有 `PixelHostFrameScope` 拥有；
- pause/stop/detach 冻结 animation active time，destroy 释放 callback、ticker、listener、输入和
  retained/render tree。

本次迁移没有改变 `PixelFrameScheduler.scheduleFrame` 的 `Unit` 返回类型，也没有替换旧
`PixelTickerProvider(PixelFrameScheduler)`、`PixelTicker` 或 `PixelHostView` 构造描述符。新增能力
是 additive API。

## 1. detach 不再等于 destroy

旧行为把 `onDetachedFromWindow` 当成释放 retained tree 的时机。这个假设无法区分临时 detach、
Fragment view 重建和真正销毁，也会让短暂离开 Window 的 Host 丢失 State。

新状态机维护两个正交轴：

| 轴 | 状态 | 含义 |
|---|---|---|
| attachment | `Detached` / `Attached` | View 当前是否属于 Window |
| owner lifecycle | `Unmanaged`、`Initialized`、`Started`、`Resumed`、`Paused`、`Stopped`、`Destroyed` | Host 是否可以运行以及是否已进入终态 |

只有以下组合会令 `lifecycleDiagnostics.isInteractive == true`：

- View 已 attach，且没有 owner，处于兼容的 `Unmanaged` 模式；
- View 已 attach，且 owner / 显式状态为 `Resumed`。

普通 detach 会使 Host 非 interactive，暂停帧、输入、手势和返回处理，但不会销毁 retained tree。
重新 attach 后，如果 owner 仍是 resumed 或 Host 处于 unmanaged 模式，原状态继续使用。

`Destroyed` 是不可逆终态。进入后重复 lifecycle、attach 或 dispose 调用都是安全的幂等操作，但
同一个 `PixelHostView` 不应再次承载新内容。

## 2. LifecycleOwner 与 ViewTree 自动绑定

`PixelHostView` attach 时调用 `findViewTreeLifecycleOwner()`。在 `ComponentActivity`、Fragment
view tree 等标准 Android 宿主中，通常不需要手工转发 `ON_START` / `ON_RESUME` 等事件。

需要覆盖 ViewTree owner 时，可以显式绑定：

```kotlin
/** Binds a custom owner that takes precedence over the ViewTree owner. */
fun bindCustomOwner(
    hostView: PixelHostView,
    owner: LifecycleOwner,
) {
    hostView.bindLifecycleOwner(owner)
}

/** Removes the explicit owner and lets an attached Host rediscover its ViewTree owner. */
fun restoreViewTreeOwner(hostView: PixelHostView) {
    hostView.unbindLifecycleOwner()
}
```

显式 owner 的优先级高于 ViewTree owner。`unbindLifecycleOwner()` 会在 View 已 attach 时重新查询
ViewTree owner；找不到 owner 时回到 unmanaged 兼容模式。

owner 到 Host 的映射是：

| Android owner 事件 | Host 状态 |
|---|---|
| `ON_CREATE` | `Initialized` |
| `ON_START` | `Started` |
| `ON_RESUME` | `Resumed` |
| `ON_PAUSE` | `Paused` |
| `ON_STOP` | `Stopped` |
| `ON_DESTROY` | `Destroyed`，终态释放 |

重复、乱序或终态后的事件不会重复注册或释放；它们会增加 diagnostics 中的
`ignoredTransitionCount`。

## 3. Fragment view lifecycle

Fragment 每次 view 重建都应创建新的 setup，并在 `onDestroyView` 终结旧 setup。即使标准
ViewTree owner 已经能发送 destroy，显式调用仍可确定地隐藏输入桥并保持自定义接线清晰；终态操作
是幂等的。

```kotlin
/** Fragment that owns exactly one PixelHostSetup per Fragment view instance. */
class PixelScreenFragment : Fragment() {
    /** Setup tied to the current Fragment view lifecycle. */
    private var setup: PixelHostSetup? = null

    /** Creates a new Host and root view for this Fragment view generation. */
    override fun onCreateView(
        inflater: LayoutInflater,
        container: ViewGroup?,
        savedInstanceState: Bundle?,
    ): View {
        // A new setup must be created after the previous view was destroyed.
        val createdSetup = createPixelHostSetup(
            context = requireContext(),
            config = PixelHostSetupConfig(content = { AppRoot() }),
        )
        setup = createdSetup
        return createdSetup.rootView
    }

    /** Destroys the current Host before releasing Fragment view references. */
    override fun onDestroyView() {
        setup?.dispose()
        setup = null
        super.onDestroyView()
    }
}
```

不要只依赖 detach 表达 `onDestroyView`。detach 现在有意保留 retained 状态；`dispose()` / `destroy()`
才是明确终态。

## 4. 没有 LifecycleOwner 的显式宿主

没有 owner 时，已 attach 的 Host 默认使用 unmanaged 兼容行为。需要完整控制运行阶段的自定义
宿主应使用显式 API：

```kotlin
/** Explicit lifecycle adapter for a Host that has no Android LifecycleOwner. */
class ExplicitPixelHostLifecycle(
    /** Host controlled by this adapter. */
    private val hostView: PixelHostView,
) {
    /** Marks the Host started without enabling dynamic work yet. */
    fun onStart() {
        hostView.start()
    }

    /** Enables rendering, input, back handling, and active-time advancement. */
    fun onResume() {
        hostView.resume()
    }

    /** Freezes dynamic work while retaining the widget and render state. */
    fun onPause() {
        hostView.pause()
    }

    /** Marks the retained Host stopped until a later resume. */
    fun onStop() {
        hostView.stop()
    }

    /** Permanently releases the Host and all lifecycle-owned resources. */
    fun onDestroy() {
        hostView.destroy()
    }
}
```

`onHostResume()` / `onHostPause()` 继续存在，并分别委托给 `resume()` / `pause()`。新代码优先使用
完整的五阶段 API。

## 5. Host-owned tickerProvider

每个 `PixelHostView` 创建独立 `PixelHostFrameScope`，并通过 `tickerProvider` 暴露当前 scope 的
provider。Navigator、动画 controller 和需要 vsync 的 widget 应使用该 provider：

```kotlin
/** Builds navigation with the provider owned by the mounted Host. */
fun buildHostNavigation(hostView: PixelHostView): PixelNavigator {
    // Always read the provider from the Host that owns this widget tree.
    val hostTickerProvider = hostView.tickerProvider
    return PixelNavigator(
        initialRoute = PixelRoute(name = "home", builder = { Text("HOME") }),
        vsync = hostTickerProvider,
    )
}
```

直接构造 `PixelTickerProvider(frameScheduler)` 仍兼容，但该 provider 不会自动加入某个
`PixelHostView` 的 lifecycle。若调用方选择独立 provider，就必须自行 pause、resume 和 dispose。

不同 Host 不得共享 `tickerProvider`。即使两个 Host 使用相同的上游 `PixelFrameScheduler`，也应
各自保留 scope、active time、ticker 和 diagnostics。

## 6. pause 与 resume 的时间策略

pause、stop 或 detach 使 Host 非 interactive 时：

- 取消当前 scope 的上游 pending frame；
- 不再请求新上游帧；
- 保留可恢复的一次性 callback 和 frame listener；
- active ticker 保持逻辑 active，但不收到 tick；
- animation active time 停在暂停前的值；
- 取消未完成手势、predictive back preview 和 pending click，并隐藏 IME。

resume 后的第一帧只重新锚定原始 frame timestamp，不把后台停留时间加入 active time；后续帧从
原值继续。因此一个暂停 60 秒的动画不会在恢复时直接跳过 60 秒。该策略是“冻结并继续”，不是
后台补帧或根据 wall clock 自动完成。

destroy 会进一步取消所有 callback，dispose 所有 ticker/listener，并释放 retained/render tree、
输入会话和缓存；它不能 resume。

## 7. frameScheduler 替换语义

`PixelHostSetupConfig.frameScheduler` 应优先在创建 Host 时配置：

```kotlin
/** Creates a deterministic test Host before any animation captures its provider. */
fun createTestSetup(
    context: Context,
    scheduler: ManualFrameScheduler,
): PixelHostSetup {
    return createPixelHostSetup(
        context = context,
        config = PixelHostSetupConfig(
            frameScheduler = scheduler,
            content = { AppRoot() },
        ),
    )
}
```

运行时设置 `hostView.frameScheduler` 会：

1. 创建使用新 scheduler 的 scope；
2. 让新 scope 遵循当前 Host lifecycle（非 interactive 时保持 paused，destroyed 时立即 dispose）；
3. dispose 旧 scope、旧 provider 及其 ticker；
4. 让后续 `hostView.tickerProvider` 返回新 provider。

它不会迁移正在运行的动画。持有旧 provider 的 Navigator/controller 会失去其 ticker；如确实需要
运行时换源，应重新读取 `hostView.tickerProvider` 并重建这些消费者：

```kotlin
/** Replaces the source and returns the new provider for rebuilding animation owners. */
fun replaceFrameSource(
    hostView: PixelHostView,
    replacement: PixelFrameScheduler,
): PixelTickerProvider {
    hostView.frameScheduler = replacement
    // The previous provider is terminally disposed at this point.
    return hostView.tickerProvider
}
```

把同一个 scheduler 实例再次赋值是 no-op。通常应避免运行时替换，除非宿主或测试明确需要切换
时钟。

## 8. diagnostics

Host lifecycle 快照：

```kotlin
// Snapshot does not retain the LifecycleOwner instance.
val lifecycleSnapshot: PixelHostLifecycleDiagnostics = hostView.lifecycleDiagnostics
```

重要字段包括 attachment、owner 状态、owner 来源、`isInteractive`、有效 transition 序号以及
attach/detach/start/resume/pause/stop/destroy 计数。

当前 Host provider 的调度快照：

```kotlin
// Re-read tickerProvider after any frameScheduler replacement.
val tickerSnapshot: PixelTickerProviderDiagnostics = hostView.tickerProvider.diagnostics()
// Host 级快照还包含 callback、listener、source frame 和 ticker 的统一所有权计数。
val frameScopeSnapshot: PixelHostFrameScopeDiagnostics = hostView.frameScopeDiagnostics
```

它报告 active/live ticker、pending frame、created/disposed ticker、dispatched frame、active time、
paused 和 disposed。`frameScopeSnapshot` 只包含基础类型，不会保留 callback/listener/ticker；自定义
宿主直接拥有 `PixelHostFrameScope` 时还可以调用
`PixelHostFrameScope.diagnostics()`，查看 callback/listener/source-frame 计数。

这些快照用于测试、soak 和调试断言，不含 callback、ticker、listener 或 owner 实例。当前 JVM
测试覆盖 60 秒 pause、resume continuity、同帧 destroy、两个 scope 隔离以及 10,000 个
ticker/listener 的终态清理；真实 Android owner、detach/reattach 继续由 instrumentation 场景验证，
不应以 JVM 测试替代设备结果。

## 9. 兼容迁移清单

| 旧用法或假设 | 1.0 行为与迁移 |
|---|---|
| detach 自动释放 runtime | detach 只暂停并保留；在真实终态调用 `destroy()` 或旧 `dispose()` |
| Fragment 只等待 view detach | 在 `onDestroyView` 调用 `PixelHostSetup.dispose()` 并丢弃旧 setup |
| Activity/Fragment 手工逐个转发 lifecycle | 标准 ViewTree owner 会自动绑定；仅在覆盖 owner 时显式 `bindLifecycleOwner` |
| 只有 `onHostPause/onHostResume` | 仍兼容；新自定义宿主使用 start/resume/pause/stop/destroy |
| app 自建并长期共享一个 ticker provider | 使用每个 `PixelHostView.tickerProvider`，不同 Host 不共享 |
| runtime 换 `frameScheduler` 后继续使用旧 provider | 旧 provider 已 dispose；重新获取 provider 并重建动画所有者 |
| pause 期间按 wall clock 继续动画 | active time 冻结；resume 从原值继续 |
| `PixelHostView.dispose()` 是独立弱清理 | `dispose()` 现在明确等价于不可逆 `destroy()` |

迁移后应至少确认：

- Fragment 每次 view generation 都创建和释放一套 setup；
- 所有 Navigator / animation 使用正确 Host 的 provider；
- pause/stop 后没有上游 pending frame 持续增长；
- destroy 后 diagnostics 中 active/live ticker、callback 和 listener 均归零；
- 需要临时 detach 保留状态的页面不再被误销毁。
