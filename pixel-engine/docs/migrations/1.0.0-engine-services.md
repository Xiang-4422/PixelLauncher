# PixelEngine 实例、服务注入与 Host capability 迁移指南

M7-2 把运行中的时钟、帧源、ticker、资源、错误、日志、主题和平台能力收口到不可变的
`PixelEngine` 实例。应用可以让多个 Host 共享一个 Engine，也可以为每个 Host 绑定不同 Engine；SDK
只共享调用方显式传入的对象。

最小 Android Host 继续只需依赖：

```kotlin
dependencies {
    implementation("com.purride:pixel-android:1.0.0")
}
```

`PixelEngine` 位于 `com.purride.pixelengine`，但随 `pixel-android` 发布；平台中立的时钟、日志、错误
事件和聚焦 capability 随 `pixel-runtime` 发布，资源缓存随 `pixel-core` 发布。旧
`com.purride:pixel-engine` 聚合坐标仍可访问这些 API。

## 创建并绑定 Engine

```kotlin
/** 当前页面独占的 Engine。 */
val engine = PixelEngine.Builder()
    .theme(PixelThemeTokens.Dark)
    .errorReporter { event ->
        crashSink.record(
            cause = event.cause,
            phase = event.phase.name,
            recovery = event.recoveryResult.name,
        )
    }
    .build()

/** 绑定 Engine 后创建的标准 Android Host。 */
val setup = createPixelHostSetup(
    context = this,
    engine = engine,
    config = PixelHostSetupConfig(content = { AppRoot() }),
)
```

已有 `PixelHostView` 可以调用 `bindEngine(engine)`。切换 Engine 会让后续帧读取新时钟、错误与日志
接收器、资源服务、Host 环境、主题和 capability，并重建该 Host 私有的 frame/ticker scope；旧 scope
会终态释放，正在使用旧 ticker provider 的 controller 必须按既有帧源迁移规则重建。

## Builder 默认值与共享规则

| 服务 | 默认行为 | 隔离规则 |
|---|---|---|
| `clock` | `PixelClock.System` | 无状态；测试可注入 fake |
| `frameScheduler` | Android `Choreographer` | Engine 保存调用方实例；每个 Host 仍有私有 frame scope |
| `tickerProviderFactory` | 为每个 Host 创建独立 provider | 不共享 ticker、active time 或 listener |
| `errorReporter` | `PixelErrorReporter.None` | 每次错误动态读取当前绑定 Engine |
| `logger` | `PixelLogger.None` | 每次日志动态读取当前绑定 Engine |
| `resourceResolver` | 原样返回逻辑 key | 只共享显式传入的 resolver |
| `resourceCache` | 每次 `build()` 新建缓存 | 即使复用同一个 Builder 也不会隐式共享 |
| `hostCapabilities` | `null`，跟随 Android 平台快照 | 显式值只覆盖绑定该 Engine 的 Host |
| `hostServices` | `PixelHostCapabilitySet.Empty` | Engine capability 优先，旧桥接只补缺 |
| `theme` | 对外读取为 `PixelThemeTokens.Default` | 只有显式调用 `.theme(...)` 才安装根主题作用域 |

最后一条是兼容约束：默认 Engine 不会把“存在默认 token”解释为“应用显式安装了主题”。旧的
scope-less facade 因而继续走历史逐像素分支；调用 `.theme(...)` 后，同一 facade 才进入 token-aware
分支。`engine.theme` 始终可安全读取完整 token 图。

## 纯 JVM fake service

测试不需要 Android Looper 或系统服务：

```kotlin
/** 测试使用的确定性时钟。 */
val clock = object : PixelClock {
    /** 返回固定运行毫秒。 */
    override fun uptimeMillis(): Long = 10L

    /** 返回固定单调纳秒。 */
    override fun nanoTime(): Long = 10_000_000L

    /** 返回固定墙上时间。 */
    override fun currentTimeMillis(): Long = 1_700_000_000_000L
}

/** 测试手工推进的帧源。 */
val scheduler = ManualFrameScheduler()
/** 不读取 Android 默认实现的测试 Engine。 */
val engine = PixelEngine.Builder()
    .clock(clock)
    .frameScheduler(scheduler)
    .resourceResolver { request ->
        PixelResourceResolution.Resolved("fixture/${request.key}")
    }
    .build()
```

访问 `PixelFrameScheduler.Default` 才会解析 Android 实现；纯 runtime 或 JVM 测试必须先注入自己的
调度器。

## 聚焦 Host capability

新 Host 服务拆成彼此独立的接口：

| Capability | 职责 |
|---|---|
| `PixelImeCapability` | 显示、更新、隐藏输入法会话 |
| `PixelClipboardCapability` | 读写纯文本剪贴板 |
| `PixelHapticCapability` | 语义化震动反馈 |
| `PixelBackCapability` | 请求 Host 返回 |
| `PixelAccessibilityCapability` | 发布辅助技术通知 |
| `PixelSavedStateCapability` | 按稳定 key 恢复、保存、删除原始状态 |
| `PixelSystemActionCapability` | 分发封闭的类型安全系统动作 |

`PixelHostCapabilitySet` 组合这些接口。缺失能力不会假装成功：无返回值调用返回
`PixelCapabilityResult.Unsupported`，读取调用返回 `PixelCapabilityValueResult.Unsupported`；能力
存在但抛异常时返回 `Failed` 并保留原始 `cause`。剪贴板或 saved state 返回
`Value(null)` 表示“支持但当前没有值”，与 `Unsupported` 不同。

类型安全 action 当前封闭为：

- `PixelOpenUriAction`
- `PixelNavigateBackAction`
- `PixelOpenAppSettingsAction`
- `PixelRequestPermissionAction`

widget 可以从 `BuildContext` 读取当前 Host 集合：

```kotlin
Builder { context ->
    OutlinedButton(
        text = "OPEN",
        onPressed = {
            /** 当前 Host 对打开 URI 的明确处理结果。 */
            val result = PixelHostServices.dispatchSystemAction(
                context = context,
                action = PixelOpenUriAction("https://example.com/help"),
            )
            if (result is PixelCapabilityResult.Unsupported) {
                showUnsupportedMessage(result.reason)
            }
        },
    )
}
```

同一 capability 同时存在于 Engine 和旧 `PixelHostBridge` 时，Engine 实现优先；Engine 未提供的 IME、
clipboard、haptic 或 system action 才由旧桥接补齐。`PixelHostBridge` 的源码和 JVM 形状保持不变，
只作为已发布消费者的兼容入口。新自定义 Host 应实现聚焦接口，不要新增字符串 action type。

## 结构化错误与恢复结果

`PixelErrorReporter` 接收 `PixelErrorEvent`：

- `cause`：保留堆栈的原始异常；
- `phase`：`BUILD`、`RENDER`、`FALLBACK_RENDER`、`HOST` 或 `RESOURCE`；
- `context`：可选 widget type、element path、render path 和 Host tag，不持有运行时对象；
- `recoveryResult`：未尝试、已恢复、无边界、恢复失败或 fallback 失败；
- `timestampNanos`：来自当前 Engine 的单调时钟；
- `attributes`：不包含敏感信息的稳定诊断字段。

Build 与 render 错误会在确定恢复结果后上报；没有边界的原异常仍抛给 Host。Reporter 或 logger
自身抛出的异常会被隔离，不会替换或掩盖引擎原异常。`PixelErrorBoundary.onError` 仍是局部 UI
恢复回调，Engine reporter 是实例级可观测通道，两者职责不同。

## 迁移顺序

1. 保留现有 `createPixelHostSetup(context, config)`，先确保行为不变。
2. 创建 `PixelEngine.Builder`，把测试帧源、资源 cache/resolver、日志和错误上报移入实例。
3. 用带 `engine` 的 setup 重载或 `hostView.bindEngine(engine)` 绑定。
4. 把新平台接线拆成聚焦 capability；旧 `PixelHostBridge` 只做过渡兼容。
5. 对每个可选能力分别处理 `Unsupported`、`Failed` 和成功结果。
6. 多 Host 测试至少使用两套主题、时钟、缓存、调度器和 Host 服务，验证没有串扰。
